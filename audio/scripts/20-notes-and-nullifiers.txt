Chapter twenty. Notes, Nullifiers, and Tachygrams.

The earlier parts of this site built a proof system that can absorb other proofs. This chapter returns to the application that system serves. The opening chapter on scaling Zcash described Tachyon in outline, with epochs, evolving nullifiers, and a window of retained values. Here we work out the objects themselves. We cover which keys a wallet holds, what a note contains, and how a wallet derives a note's nullifiers for each epoch. We also cover why a spend publishes two of them, and why every action publishes exactly two values of a single kind.

We do not cover how a proof refers to the pool's history or how a spender shows absence from old epochs. The next chapter builds the pool state, the chapter on oblivious sync covers absence proofs, and the chapter on the proof tree walks through the steps that prove all of this.

A caution about the status of these designs. Tachyon has not activated on mainnet and its design is still changing. Everything here describes the Tachyon repository at the commit this site pins, whose shielded protocol specification is still an empty outline. The book's own key hierarchy page carries a note calling itself significantly outdated, and the book's analysis of nullifiers presents its choice as a recommendation with an alternative. Where the sources differ, we give both and follow the code unless we say otherwise.

Our accounts of what each proof step computes and checks are reconstructed from the code at the commit this site pins, and the authors have not confirmed them. Tachyon also pins a different revision of Ragu from the one the earlier chapters read.

Fields and stand-ins.

Tachyon's objects live in two fields. Pallas, the curve used for spend authorization, has coordinates in one field and scalars in another. Poseidon's inputs and outputs, and therefore all tachygrams, are elements of the coordinate field, and signing keys are elements of the scalar field. The toy curve has the same shape, with coordinates modulo thirty-one and scalars modulo forty-three, so we use it for every signing key below.

The hashes need a different treatment. Tachyon uses Poseidon throughout, which the chapter on statements and challenges introduced, and each use has its own domain. In a field of thirty-one elements, unrelated hash outputs would collide constantly, and that would hide the behaviour we want to see. So the examples use a stand-in, which is SHA two fifty-six of a tag and the inputs, reduced modulo sixty-five thousand five hundred thirty-seven. A stand-in sponge produces four such values from one call.

These numbers are not Poseidon outputs and are not elements of the toy field. They only show the structure, and the small range is useful later, because it lets us count a cheater's chances exhaustively.

The spending key and its two children.

Spending a note requires two separate abilities. The owner has to authorize the spend with a signature, and the owner has to produce the note's nullifiers, which nobody else should be able to compute. The book's deep dive observes that these are the only two abilities the shielded protocol needs from its keys. Everything else in Orchard's key tree, including viewing keys and diversified addresses, supports delivering notes to recipients and detecting them. The opening chapter explained that delivery has moved to a separate payment protocol.

The root is a spending key of thirty-two random bytes, and each ability gets one child derived from it. Both children come from the same keyed hash, which Zcash calls the expansion function. It runs BLAKE two b over the spending key and a one-byte domain, with a fixed personalization string that keeps it apart from other uses of BLAKE two b. It returns sixty-four bytes. The wallet reads those bytes as an integer and reduces it into whichever field the key needs.

In the toy we replace BLAKE two b with SHA two fifty-six. We reduce modulo forty-three for the first child and modulo sixty-five thousand five hundred thirty-seven for the second, which is the stand-in hash range.

The first child is the spend authorizing key, a scalar, and its public point is the spend validating key. The second child is the nullifier key, an element of the coordinate field, and it has no public counterpart.

One detail comes from RedPallas, the signature scheme that Orchard and Tachyon share. It requires the spend validating key to have a cleared sign bit in its compressed encoding. In Orchard this rule lets the x coordinate alone determine the key, and Orchard's key derivations rely on that. Tachyon's payment key hashes both coordinates, so nothing in this chapter depends on the rule, and it stays for compatibility with the signature scheme.

The rule has one visible effect. A point and its negative have the same x coordinate and opposite signs of y. So if the derived point has the wrong sign, the code negates the spend authorizing key, which negates the point. On the toy curve we use the parity of y as the sign.

Here is Alice's wallet. Our generator is the toy point one, two, and the spending key is a short text standing in for random bytes. Expanding it gives the scalar nineteen, whose public point is twenty-seven, one, with an odd y coordinate. So the wallet negates the scalar, giving twenty-four modulo forty-three. Its public point, the spend validating key, is twenty-seven, thirty, with an even y coordinate. The nullifier key comes out as forty thousand nine hundred fifty-four.

Proofs do not check these derivations from the spending key. The deep dive says that the circuits use the spend validating key and the nullifier key as witnesses and never constrain how they arose. A wallet standard chooses the path, and the protocol only needs the results to look like randomly sampled keys.

The payment key.

A sender has to name the owner of a new note. Publishing the two keys to the sender would give away the nullifier key, so the note carries a commitment to the pair. The payment key is a Poseidon hash of the two coordinates of the spend validating key together with the nullifier key.

A wallet does not hand one payment key to every sender. The payment key is a deterministic function of the pair, so two senders who received the same payment key could compare notes and learn that they paid the same person. So unlinkability comes from minting a fresh address per sender. The wallet keeps a master seed, derives one spending key per sender at successive indices, and runs the same derivations on each.

With Alice's first key, the stand-in gives the payment key thirty-five thousand five hundred seven. For a second sender, her wallet moves to the next index and gets a new spend validating key and a new nullifier key. The payment key is then three thousand two hundred seventy. Nothing in these two payment keys shows that they belong to one wallet.

Orchard reaches unlinkable addresses differently, from a single key. Each Orchard address carries a public diversifier, which hashes to a base point. The address's key is a fixed secret scalar multiplied by that base point. Anyone holding that secret can produce as many addresses as they like, and the curve arithmetic hides that they share it.

A hash output offers no comparable operation, because nobody can turn one output into another related one without the inputs. So Tachyon needs a separate key pair for each sender.

The book gives two reasons for accepting this cost. First, the diversified-base construction has no known secure analogue under lattice assumptions, which matters for a future move away from elliptic curves. Second, a design that handed the spend validating key to senders would let a sender who kept it attack it later with a quantum computer.

The hash also binds the nullifier key to the note's owner field, and we'll soon see that this is what stops a spender from inventing a second nullifier sequence.

The wallet can also separate proving from signing. The proof authorizing key is the pair of the spend validating key and the nullifier key. It gives a device what it needs to build proofs for every note paid to the matching payment key, and it cannot sign. So a hardware wallet can hold the spend authorizing key while another device does the proving.

Here is what each key allows. The spending key allows everything. The spend authorizing key signs for spends, after randomizing. The nullifier key computes nullifiers given a note's nullifier trapdoor, and so sees when the note is spent. The proof authorizing key builds proofs without signing. The payment key, which senders hold, only receives notes.

With one key pair per sender, a proof authorizing key covers the notes paid to one address. The sources disagree about this scope. The key hierarchy page and a code comment call the nullifier key wallet-wide, so that one proof authorizing key would cover all of a wallet's notes. That does not fit a fresh pair of keys per sender.

The code at the commit this site pins witnesses a full proof authorizing key for each note it proves, and a comment on the type says that proof delegation is yet to be specified. This site follows the per-sender reading and treats the scope of delegation as unsettled. A sync service, by contrast, receives only values and no key material.

Notes and commitments.

A note has to record who owns it and what it is worth, and it needs enough randomness to stay hidden and to have nullifiers of its own. Tachyon's note has exactly four fields. They are the payment key, a value in zatoshi between zero and two point one times ten to the fifteen, a nullifier trapdoor, and a commitment trapdoor.

The nullifier trapdoor gives the note its identity for nullifier derivation. The commitment trapdoor hides the note inside its commitment. Compared with Orchard's note, the diversifier and transmission key have become the payment key, and the field called rho has gone. We'll return to what removing rho costs.

The sender chooses both trapdoors and so knows all four fields, as the threat model assumes. The recipient has to learn them as well, through whatever payment protocol the two wallets use. How to generate the trapdoors is unsettled. The deep dive says they should come from a standardized derivation off a wallet key. The code comments say they can come from a key negotiated out of band, and we found no standard at this commit.

Suppose Bob pays Alice twenty-five zatoshi using her payment key. The nullifier trapdoor is six hundred twenty-five, and the commitment trapdoor is a larger random value. Bob and Alice both know all four fields, and Alice gave Bob only the payment key.

Bob cannot publish these values, so he publishes a note commitment that fixes all four. It is a Poseidon hash of the commitment trapdoor, the payment key, the value, and the nullifier trapdoor. For our note the stand-in gives fifty-five thousand six hundred ninety-seven.

Sapling and Orchard use variants of the Pedersen commitment, which rely on discrete log, and Tachyon uses a hash alone. Each Tachyon use of Poseidon starts its sponge with zero rate cells and with the sixteen-byte domain name, read as a number, in the capacity cell. So different domains behave as unrelated hash functions, even on identical inputs, and the padding tachygram later relies on this.

Changing only the commitment trapdoor gives the commitment fifteen thousand eight hundred eighty-three, which looks unrelated to the first, although the note has the same owner, value, and nullifier trapdoor. A random commitment trapdoor is what lets the commitment hide two notes with the same owner and value from each other. Hiding here assumes that Poseidon behaves like a pseudorandom function.

Randomizing the signing key for each action.

Everyone has to be able to check a signature, so its verification key must be public. If that key were the spend validating key, every spend under that key would carry the same public key, and an observer could link them all. So spend authorization works as in Orchard.

Each action picks a scalar, called alpha, and signs with a randomized key, which is the spend authorizing key plus alpha. The matching public key is the spend validating key plus alpha times the generator. Scalar multiplication distributes over addition, so that point is exactly the public key of the randomized signing key. The action publishes the randomized public key, and the proof shows that it came from the spend validating key inside the note's payment key.

Tachyon derives alpha from per-action entropy and the note commitment, with a Poseidon hash read as a scalar. That reading is possible because the coordinate field is smaller than the scalar field. This ties the key to the note, and it lets a signing device recompute alpha from the note and the entropy without having to trust a value handed to it. Our stand-in output is far larger than forty-three, so here we reduce it modulo forty-three, which the real construction does not do.

In our run, alpha is twenty-three. The randomized signing key is twenty-four plus twenty-three, which is four modulo forty-three. Adding twenty-three times the generator to the spend validating key gives the point twenty-four, thirty. Four times the generator gives the same point, as it should.

A signature follows the Schnorr pattern. With a nonce of nine, the signer computes the nonce's point, nine, twenty-two, and derives a challenge of eighteen from a hash of that point, the randomized key, and the message. It returns nine plus eighteen times four, which is thirty-eight modulo forty-three. The verifier checks that thirty-eight times the generator equals the nonce's point plus eighteen times the randomized key. Both sides equal twenty-six, twenty-three, and the verifier never used the spend validating key.

The published key reveals nothing about the spend validating key when alpha is uniform. Adding a uniform multiple of the generator produces a uniform point, whatever the starting key. We can test this exhaustively on the toy curve. Of the forty-two points other than the identity, twenty-one have an even y coordinate and could be a normalized key.

For each of those twenty-one candidates, exactly one alpha turns it into the published point twenty-four, thirty. So the published key is equally consistent with every owner. A second action by Alice, with alpha equal to thirty-two, publishes the unrelated-looking point six, twenty-three.

An output action has nothing to authorize, since creating a note spends nobody's money. It still has to look like a spend, so it also publishes a key and a signature, with the signing key equal to alpha alone. It uses the domain Tachyon Output in place of Tachyon Spend. Both shapes produce a uniform point. Each action also publishes a value commitment, which the chapter on the proof tree covers.

Deriving a note's nullifiers.

The opening chapter set out what an epoch nullifier has to do. A note needs a different nullifier in each epoch, these values must look unrelated to anyone without the owner's secret, and each epoch must have exactly one valid value. A wallet might also need many of them at once, because a proof about an old note covers every epoch since its creation. These needs lead to a derivation in two stages.

The first stage combines the two secrets that make a nullifier belong to this owner and this note. It hashes the nullifier trapdoor and the nullifier key to produce the note's master key. Only the recipient knows both inputs, because the sender lacks the nullifier key and nobody else learned the trapdoor. Computing the master key once also means the later nullifier computations need only the master key, so the wallet's nullifier key does not have to travel further through the proof. Our note's master key is two hundred ninety-nine.

The second stage turns the master key and an epoch into nullifiers. One Poseidon permutation yields a whole rate's worth of output, so four values cost the same as one. Wasting three of them would be a poor use of a limited circuit, and Tachyon takes all four and assigns them to four consecutive epochs.

To find the value for an epoch, round the epoch down to the start of its group of four. Run one sponge over the master key and that group start, and take the entry at the epoch's position in the group. For epoch seven, the group starts at four, and the nullifier is the entry at position three.

Here is the running note's sequence, created in epoch three and spent with target epoch seven. The sources also call the target epoch the anchor's epoch or the present epoch. The nullifiers for epochs zero to two come from before the note existed. Those for epochs three to six get tested for absence.

The nullifiers for epochs seven and eight get published by the spend. They are fifty-five thousand one hundred thirteen and sixty-one thousand one hundred seventy-seven, and we'll meet both again. The nullifiers for later epochs are never revealed.

A value depends only on the master key and the epoch, because each group absorbs its own start. So two derivations that overlap agree on the epochs they share, and the script asserts this for our note.

Both inputs matter. A second note to Alice, with a different nullifier trapdoor, has a different master key and a different nullifier for epoch seven, so her two notes do not share nullifiers. Bob knows the first note's trapdoor, but his own nullifier key gives a different master key. His value for epoch seven is fifty-five thousand five hundred seventy-six, where the true value is fifty-five thousand one hundred thirteen. So the sender of a note cannot watch for its spend.

The privacy argument assumes that Poseidon, keyed by the master key, behaves as a pseudorandom function. Revealing some outputs then says nothing about the others, including the pair revealed at spend time.

The code allows epoch indices up to one million forty-eight thousand five hundred seventy-five, since a block height has thirty-two bits and an epoch has four thousand ninety-six blocks. At seventy-five seconds per block, that range lasts about ten thousand two hundred seven years.

The sources differ on the nullifier's inputs. The deep dive hashes the nullifier key and then the trapdoor, and its sponge absorbs the epoch divided by the rate and rounded down. It calls this the leading candidate. The nullifier page and the code, at the commit this site pins, have the master key absorb the trapdoor first, and the sponge absorbs the group-aligned epoch.

For epoch six, the deep dive absorbs one while the code absorbs four. In our stand-in the two choices give different values, so they are different functions, although each gives every epoch one fixed value. This site follows the code. Some code comments still describe older designs, so we rely on the functions rather than their comments.

Why the wallet derives its own nullifiers.

A reader might expect a design in which the wallet hands a sync service a key for a range of epochs, and the service computes the nullifiers itself. An earlier Tachyon design did this, and the book keeps it as an archived page. Proof cost is the reason it was replaced, and a comparison makes that concrete.

The archived design used the GGM construction, which treats an epoch's bits as directions down a binary tree. A seed sits at the root, each node has two children given by two hashes, and each leaf is a nullifier. Hashes are one-way, so holding a node gives access to the leaves below it and to nothing else, which is exactly a key for a range of epochs.

Take a space of eight epochs, written with three bits. To delegate epochs two and three, a wallet hands over only the node above them, reached by going left and then right from the seed. Walking one more level from that node gives exactly the nullifiers for those two epochs. One-way hashing keeps the holder away from all the others.

The range of epochs zero to six needs three such nodes. Over all ranges in this small space, the worst case needs four, reached by epochs one to six. So the amount of delegated key material depends on the range.

The trouble is that each level of the tree costs one hash inside a proof, and proof steps are small. The analysis counts it this way. A step has two thousand forty-eight multiplication gates, and one Poseidon permutation costs two hundred eighty-eight of them, so a step fits seven permutations.

A binary tree over an epoch space of two to the fourteen days, about forty-five years, has depth fourteen. So one walk takes fourteen permutations and overflows a step. The analysis counts epochs as days here, unlike the code's epochs of four thousand ninety-six blocks, but only the depth matters for cost.

A node with four children costs one permutation, the same as a node with two, because one permutation emits four outputs. So raising the arity shortens the walk at no extra cost per level. Seven levels with four children each already cover two to the fourteen leaves, and a walk of depth seven just fits a step.

The analysis wants at least two nullifiers in one step, since a spend publishes two, and a tree walk cannot provide that. It then tries other constructions and recommends using a Poseidon permutation directly, with its output of four values. The analysis calls this attempt three, and it is the design we just described.

Compare the costs per step of seven permutations. The binary tree fits no nullifier at all, since one walk overflows a step. The tree with higher arity fits one. One hash per nullifier fits seven. Taking all four outputs of each permutation fits seven times four, or twenty-eight.

This construction gives up the range key, because a plain hash has no partial key to hand out. The trade is that wallets derive and prove their own nullifiers, and they send the service explicit values. The service then holds a finite list and can compute nothing beyond it. The chapter on oblivious sync shows how the wallet later ties the service's work to its note.

The analysis and the code differ on nullifiers per step. The analysis counts up to twenty-eight per step, and its conclusion also offers an alternative based on a hash called MiMC. The code at the commit this site pins derives a batch of sixteen consecutive nullifiers per step, which is four sponges, and the sources do not explain the choice of sixteen. The code calls such a batch a window. It has nothing to do with the two-epoch window that validators keep, so this chapter says batch.

How the commitment pins the nullifiers.

Publishing a nullifier only prevents double spends if a spender has no choice about its value. If a spender could produce two nullifier sequences for one note, the second sequence would pass both the exclusion proof and the window, since neither has ever seen those values. The note commitment has to rule this out, and it does so through a chain of hashes.

Follow the chain from the top. The spend validating key and the nullifier key feed the payment key. The payment key, the value, and the two trapdoors feed the note commitment. Separately, the nullifier trapdoor and the nullifier key feed the master key, and the master key and an epoch give the nullifier for that epoch. The epoch is public, and every other input is secret.

The proof recomputes every one of those hashes. The spender supplies one opening of the note as private inputs, meaning the spend validating key, the nullifier key, the value, and the two trapdoors. From that one opening the proof computes the payment key, then the commitment, then the master key and the nullifiers. The nullifier trapdoor and the nullifier key feed both the commitment and the master key, so the commitment and the nullifiers cannot come from different openings.

On its own this proves little, since a spender could invent any opening and compute a commitment for it. A separate part of the proof closes the gap, and the chapters on pool state and on the proof tree build it. That part shows that this commitment was already published in the pool when the note was created. A spender who invents an opening gets a commitment that nobody published, and that part of the proof fails. So the spender is held to an existing commitment, and both inputs to the master key sit behind it.

To cheat, a spender would keep the commitment fixed while changing what lies behind it. Our small hash range allows us to try every possible change to one field at a time, which is sixty-five thousand five hundred thirty-six wrong values per field. One wrong nullifier key keeps the commitment the same, and so does one wrong nullifier trapdoor. Either would give the cheater a second nullifier sequence.

Two wrong values also match, which would give a different value for the same note. Two wrong commitment trapdoors match as well, which gives nothing useful, since the note is otherwise the same.

A random function into that range should produce about one match per field. The search finds six matches in total, and each of them is a real collision. For one wrong nullifier key, the payment key still comes out as thirty-five thousand five hundred seven, so the commitment stays the same. Meanwhile the master key changes, and so does the nullifier for epoch seven. On this toy scale a cheater could double spend.

The attack succeeds here only because the range is small. The protection comes entirely from the assumption that nobody can find such a collision, so it needs a hash with a far larger range. Real Poseidon outputs have about two hundred fifty-five bits, and a search of the kind we just ran would be hopeless.

Two further assumptions complete the argument. The proof system must not allow a false statement to verify, and the proof must really compute these hashes. We qualify that last assumption near the end of this chapter, since these steps do not yet run as real circuits.

The published nullifiers follow the same pattern. The proof computes them from the master key and the epoch, so the spender never gets to supply a nullifier directly. The same chain also blocks an inflated spend. The two matches for the value field are toy collisions of this kind, since each gives the same commitment a different value, and the realistic range rules them out for the same reason. With such a range, a spender who keeps the trapdoor and nullifier key but claims a larger value gets the right nullifiers and a different commitment. Nobody published that commitment.

Reusing a trapdoor.

Nothing in the protocol forces the nullifier trapdoor to be unique, because the pool holds an unordered set of values and gives notes no position to bind to. Orchard avoided this by setting a new note's rho to the nullifier of a spent note, and consensus already forbids repeated nullifiers. Tachyon cannot enforce that binding, and a malicious sender can exploit this.

Suppose Bob sends Alice a second note with value nine, a new commitment trapdoor, and the same nullifier trapdoor of six hundred twenty-five. Its commitment differs from the first, so it looks like a separate note. But the payment key fixes the same nullifier key, so both notes have the master key two hundred ninety-nine. They have the same nullifier at every epoch.

Once Alice spends one of them, the other can never be spent, because its nullifiers have already been published. A wallet detects this on receipt by computing one nullifier at a fixed reference epoch for each incoming note. With reference epoch zero, both notes give the same value, and the wallet rejects the second.

This is the faerie gold attack, in which a recipient holds money that turns out not to be spendable. It harms the recipient and creates no money, and Tachyon moves the defence out of consensus. A wallet's own note set is small, which keeps the comparison cheap.

The sources differ on this attack too. The deep dive says it remains possible in principle, and that resisting it becomes the responsibility of the payment protocol, through the wallet check we just described. The code comments at the commit this site pins call the attack moot under out-of-band payments, and say that nullifiers need no collision resistance. The nullifier page separately warns that notes should not reuse the trapdoor.

We did not find a wallet check in the crate. This site follows the deep dive here, since our example shows that the attack works, and out-of-band delivery does not change the arithmetic.

Why a spend publishes two nullifiers.

The opening chapter stated the rule and argued in two cases that it catches every double spend. Validators accept a stamp for an epoch during that epoch or the next, and they keep the tachygrams of the current and preceding epochs. A spend with a given target publishes the nullifiers of the target epoch and of the epoch after it. This section builds on that argument rather than repeating it.

It adds three things the opening chapter left out. These are an example of the attack that a single nullifier would allow, the reason the window spans two epochs, and a check of every case on the running note.

A later proof looks for each nullifier only in the epoch with the same number. So a spend has to leave a value where such a test will find it. The grace period threatens exactly this, because a spend with a given target may land in the next epoch.

Suppose instead that a spend published only its target's nullifier. A first spend with target seven waits in the mempool and gets accepted in epoch eight, so epoch seven's nullifier lands in epoch eight. A second spend with target eight now tests epoch seven's nullifier against epoch seven, where it is absent. It publishes epoch eight's nullifier, which nobody has published. Both checks pass and the note is spent twice.

Publishing the next epoch's nullifier as well closes this gap. A spend is accepted either in its target epoch or in the next one, and the pair covers both. So a spend accepted in some epoch always publishes that epoch's own nullifier during that epoch.

Picture a grid of epochs six to nine, where each epoch tests whether the nullifier with its own number is absent. A pair accepted in epoch seven places epoch seven's nullifier in epoch seven, where that test fails. A pair accepted in epoch eight places epoch eight's nullifier in epoch eight, where that test fails too. A lone epoch seven nullifier accepted in epoch eight matches no test.

To check cases by number, we write the opening chapter's two cases more carefully. Take a first spend and a second spend of the same note, with the second accepted no earlier than the first.

The first case is when the second spend's target comes after the epoch in which the first was accepted. Then the second exclusion proof would have to show that epoch's nullifier absent from that epoch. The first spend put it there, so the prover cannot build the proof.

The second case is when the second spend's target is no later than the first spend's acceptance epoch. The second spend's acceptance is no earlier than the first's, and it is at most one epoch past its own target. So the first acceptance epoch is at most one past the second target. Together with the case, this means the first acceptance epoch is either the second target or the epoch right after it. The second spend's pair therefore repeats the value the first spend left.

The same bounds explain the length of the window. The second acceptance is at most one past the second target, and the second target is no later than the first acceptance. So the second acceptance is at most one epoch after the first. The repeated value can arrive one epoch after the first copy entered the pool, so validators have to still hold the epoch before the current one.

Take two spends with target seven, the first accepted in epoch seven and the second in epoch eight. The colliding values, fifty-five thousand one hundred thirteen and sixty-one thousand one hundred seventy-seven, entered the pool during epoch seven. A validator that kept only the current epoch would miss them when the second spend arrives.

The argument assumes that a spender cannot choose nullifiers, which the commitment chain covered, and that nobody can forge proofs. The opening chapter's table only followed a first spend that landed late, in epoch eight. Our table adds a first spend that lands on time, in epoch seven. When the second spend lands in the window, both publish the same nullifier. When its target is later, the first spend's nullifier is already present in the epoch the second proof must clear.

The script checks this on every pair of spends of our note, with targets from epoch three to epoch nine and each spend accepted in its target epoch or the next. There are one hundred eleven such scenarios. In seventy-two of them the second target comes after the first acceptance, and the second proof cannot be built. In the other thirty-nine, consensus finds a shared value in its window. No scenario escapes.

The two checks also overlap in six scenarios, where the first spend was accepted on time and the second targets and lands in the very next epoch, so the window would have caught it too. Rerunning the same one hundred eleven scenarios with a single published nullifier per spend lets forty-eight of them through, as in the example earlier.

This argument is reconstructed from the code at the commit this site pins, and the authors have not confirmed it. The rules come from the deep dive's consensus section, which argues by listing the safe cases for each acceptance time. The single fact about each epoch's own nullifier and the two-case argument are our restatement. The spend bind step derives the pair as described, and a comment on the tachygram type states the window rule, but we did not find the window scan itself in the crate.

The tachygram page adds a second reason for scanning a whole epoch, since a stamp's anchor can advance within its epoch. The next chapter explains it.

Publishing the pair has a cost in the circuit, because the two values do not always come from one sponge. Our note's pair shows why. Epoch seven's nullifier comes from the group starting at four, while epoch eight's comes from the group starting at eight, so this pair needs two sponges. A spend with target five would find both of its values in the group starting at four.

A circuit's shape cannot depend on secret values, as the arithmetization chapter explained, so the spend bind step runs two sponges in every case. The pair also needs a following epoch, so the code refuses a spend in the final epoch.

Tachygrams and output padding.

Earlier Zcash pools keep commitments in a Merkle tree and nullifiers in a separate set. Tachyon instead treats both as one kind of value, a tachygram, which is a thirty-two byte element of the coordinate field. A single structure can answer both questions a spend asks, namely whether a commitment is present and whether a nullifier is absent. Consensus does not need to know which kind a value is. This also helps privacy, as long as the published values give no other hint of their kinds.

Counting gives such a hint. A bundle already reveals its number of actions, because each action has one signature. A spend publishes two nullifiers and an output has only one commitment, so without further care the total would reveal the split. For now we leave aside the bundle's fee change note, because it adds the same one value in every case.

Take four actions. With no spends the total is four, with one spend it is five, and with four spends it is eight. An observer who subtracts the number of actions from the total gets the number of spends.

The deep dive notes that the leak is only about the count, since tachygrams never sit beside a particular action. To remove it, each action publishes exactly two. A spend publishes its pair, and an output publishes its commitment and a padding tachygram. So four actions now publish eight tachygrams, whatever the split.

The pad cannot be any easily computed function of the commitment. To see what an observer could do if it were, take one bundle with four actions, two of each kind. It publishes two tachygrams per action plus one for the fee change note, which makes nine, and the stamp lists them in sorted order.

Suppose first that each output derived its pad as a hash of its commitment. Only the two pads would change. An observer holding the nine published values hashes each one and looks for the result among the others, which takes seventy-two ordered comparisons. The test finds exactly two matches, one for each output's commitment. So the observer learns which values are commitments and how many outputs the bundle has.

Now run the same seventy-two comparisons on what Tachyon actually publishes, where each pad comes from the note opening. They find no matches. To test the real relation, the observer would need all four fields of the note.

So Tachyon derives the pad from the note opening, as a Poseidon hash of the same four inputs as the commitment, under a different domain. The hiding that the commitment gets from its trapdoor also hides any relation between the two values. The domain tag is the only thing separating the pad from the commitment.

The sources differ on the pad's construction. The deep dive hashes an arbitrary preimage and calls the result a dummy. The tachygram page and the code, at the commit this site pins, have the pad commit to the note opening, and the output bind step computes both values from the note. Both forms resist the pairing test, so the disagreement is about construction, and this site follows the code.

One value in our bundle falls outside the pairs. Each bundle's fee change note publishes only its commitment, even when its value is zero. So a stamp holds two tachygrams per action plus one per bundle. The extra one appears once per bundle whatever the bundle does, so it adds nothing about the split.

Some book pages still count one tachygram per action, and as in the opening chapter we follow the code's two. The chapter on aggregation and bundles covers fees.

A stamp holds its tachygrams as a flat list, and the wire format requires them to be unique and sorted by their byte encoding. Sorting erases the order in which actions contributed them, and in the code a spend's step commits its pair as a set. Every published value is also required to be nonzero. The deep dive ties this rule to the set polynomial, which the next chapter builds, and we leave the explanation to that chapter.

These privacy statements cover what the published values reveal. As the chapter introducing proof-carrying data records, Ragu's book and code do not yet establish zero knowledge. So a separate question remains about what a proof itself reveals.

One structure for both tests.

We can now see why one kind of value is enough. A stamp's set of tachygrams corresponds to the polynomial whose roots are its members. A value is present exactly when the polynomial vanishes there, and absent when it does not, and neither test cares about the kind of value.

For our bundle, working modulo sixty-five thousand five hundred thirty-seven, the polynomial vanishes at the first output's commitment. It also vanishes at the first spend's nullifier for epoch seven, and the test has no need to know which kind each root is. Epoch nine's nullifier was not published, and the polynomial is nonzero there.

A spender uses the first kind of test to show that its commitment was published, and the second to show that an old nullifier was not. The next chapter develops these polynomials and their commitments.

Where these derivations run.

Each object in this chapter is computed inside a step of the proof tree, and the wallet runs all of these steps. The chapter on the proof tree walks through them in order.

Note seed derives the payment key from the proof authorizing key, then the master key and the commitment from one opening. It passes the master key on in place of the nullifier key. Spendable init requires the commitment to be among the tachygrams of the stamp that created the note. Nullifier derive computes a batch of sixteen consecutive nullifiers from the master key.

Spend bind derives the published pair from the master key and checks that both values are nonzero. It also checks the note's commitment against the one carried from spendable init. Spend action witnesses the proof authorizing key again to check it against the payment key, derives alpha and the randomized key, and commits the pair. Output bind derives the commitment and the pad from a note.

What comes next is reconstructed from the code at the commit this site pins, and the authors have not confirmed it. At this commit, Tachyon builds Ragu with its mock feature, and these steps compute hashes natively. Comments mark the known gaps. A real circuit needs a low-bit decomposition of each epoch to find the group start, since any field element can be written as four times something.

It also needs a bit decomposition of alpha to use it as a scalar. So our statements about what a proof forces describe the design that the steps declare, and we did not find real circuits enforcing them in this crate. The gate counts we quoted come from the analysis page, and they are estimates for those circuits.

Where this chapter leaves us.

Let's collect what we've built. A wallet derives two children from its spending key, one to authorize spends through its public point and one to derive nullifiers, and no proof constrains these derivations. The payment key hashes the public signing point and the nullifier key, so it reveals neither. Wallets mint a fresh one per sender, because a hash has no counterpart to Orchard's diversified addresses.

A note holds a payment key, a value, and two trapdoors, and its commitment is a domain-tagged Poseidon hash of those fields. The sender knows all four fields but not the nullifier key. Each action signs with a key randomized by alpha, so a published key is consistent with every possible owner, and outputs use the same form with no spending authority.

A note's master key hashes the nullifier trapdoor and the nullifier key. One sponge over the master key and a group start gives four consecutive epoch nullifiers, and cost in the proof is the reason this replaced the archived GGM tree. Both inputs to the master key sit behind the commitment, so a spender held to a published commitment has one nullifier sequence, assuming Poseidon resists collisions. Reused trapdoors remain a danger that the wallet must detect.

A spend accepted in some epoch always publishes that epoch's nullifier during that epoch. This single fact, the exclusion proof, and a two-epoch window together catch every double spend. Commitments and nullifiers are published as one kind of value. Each action publishes two tachygrams and each bundle one more, so an observer learns the number of actions and not the split between spends and outputs.

All of this is a design at one commit of a proposal that has not activated, and these steps still run against a mock of Ragu. We have spoken of values being published in the pool without saying how a proof can refer to history that validators have forgotten. The next chapter, Pool State and Anchors, builds that structure. It starts from the set polynomial, commits to it as a single curve point, and then folds those points into the hash chain of anchors.
