Chapter one. Scaling Zcash.

Zcash lets people pay each other without publishing who paid whom or how much. The cryptography that provides this privacy also creates two costs that grow with use. Every validator must remember a value for every note ever spent, and every wallet must examine every payment on the chain to find its own. Neither cost matters much at low volume. Both become serious limits if shielded payments are to grow by orders of magnitude.

Tachyon is a proposal to remove these two limits, and Ragu is the proving system built to support it. This chapter explains the problem and the outline of Tachyon's answer, and it ends with the requirements that answer places on a proof system. It contains no proof machinery. The rest of the site builds that machinery, and later chapters return to Tachyon in detail.

A word on Tachyon's status comes first. Tachyon is a proposal, and it has not activated on Zcash mainnet. Its design is still changing, and the sources sometimes disagree with one another. At the commit this site pins, the network upgrade deployment ZIP is an empty outline. The crate at that commit builds against a mock of Ragu, so its proof steps run natively with no real circuits, and we did not find a validator in it. Statements about Tachyon in this chapter describe the design at that commit, and they may not describe what eventually ships.

Hiding payments on a public ledger.

A public ledger has to convince everyone that no money was created or spent twice. Transparent systems do this by showing every balance. Zcash's shielded pools have to reach the same conclusion from data that reveals no amounts or parties.

The Zerocash paper achieved this with a zero-knowledge proof, which is a short object that convinces a verifier that a statement is true while revealing nothing beyond that fact. Later chapters construct such proofs, and for now we treat one as a black box. The prover holds some secret data, the verifier holds a public statement about it, and the verifier learns only that the statement holds.

The next few sections describe how shielded payments use such proofs today. We follow Orchard, the Zcash shielded pool that Tachyon's design starts from, and we leave out details that do not affect the scaling problem.

Notes and commitments.

Shielded money exists as discrete notes. A note resembles a banknote with a named owner, because it records a value, the recipient, and some random values that make it unique. Orchard writes the recipient as two parts, a diversifier and a transmission key. The random-looking values have the names rho, psi, and r c m, and we'll explain the first two shortly.

The note cannot appear on the chain, since that would reveal its value and owner. So a transaction that creates a note publishes a note commitment instead, which is a short value computed from all the note's fields. As with the vector commitments of a later chapter, the commitment fixes the note's contents without revealing them, because the random value r c m masks everything else.

A spender later has to show that the note being spent really was created. Validators collect all commitments into a Merkle tree of depth thirty-two, and the tree's root at a given moment is called an anchor. The spender proves in zero knowledge that it knows a note whose commitment is a leaf under a recent anchor. The proof reveals neither the note nor the leaf's position, so nobody can link the spend to the output that created it.

Nullifiers.

Hiding which note is being spent creates a new problem. Validators cannot mark a leaf as spent, because they do not know which leaf is involved. Without some further mechanism, one note could be spent repeatedly with a new proof each time.

To close this gap, the spender publishes a second value, called the nullifier. The note determines its nullifier uniquely, and the proof shows that the published value is the correct one for the note. Validators keep a set of all nullifiers seen so far and reject any transaction that repeats one.

Two properties make this work. First, the nullifier must be unlinkable to the commitment, or publishing it would reveal which note was spent. Second, only the owner should be able to compute it, or the sender of a note could watch for it and learn when the recipient spends the money.

Both properties come from deriving the nullifier with the owner's secret nullifier key. Leaving out some curve details, Orchard's derivation works like this. Apply a keyed pseudorandom function to rho, using the nullifier key. Add psi to the result, multiply a curve generator by that sum, and add the note commitment. The nullifier is the x coordinate of the resulting point. Orchard sets a new note's rho to the nullifier of the note spent in the same action. That keeps each rho distinct, because consensus already forbids repeated nullifiers.

A small ledger shows how the pieces fit together, using a shortened S H A two five six whose values only illustrate the structure and are not Orchard values. Alice owns a note worth forty, and Bob owns two notes worth twenty-five each. Bob's two notes have the same owner and value, yet their commitments and nullifiers look unrelated, because each note has its own random values.

Now suppose Bob spends his first note. He publishes its nullifier and proves in zero knowledge that it belongs to some commitment in the list. The validators see that the value is new, accept the spend, and add it to the nullifier set. If he tries again, the proof forces him to publish the same value, and the validators reject it. An observer cannot match the nullifier to Bob's commitment, because matching them requires Bob's key. A third person, Carol, could not compute this nullifier either, since her key gives a different value for the same note.

An Orchard transaction contains a bundle of actions, and each action pairs one spend with one output. ZIP two twenty-five fixes an action's encoding at eight hundred twenty bytes, which include the nullifier, the new note's commitment, an ephemeral key, and two ciphertexts of five hundred eighty and eighty bytes. We'll return to those ciphertexts when we reach wallets.

Why the nullifier set grows forever.

The nullifier set has an unusual property, which is that its entries can never become irrelevant. A note has no expiry date, so its owner might spend it decades after receiving it. To reject a repeat of a spend from ten years ago, a validator needs the nullifier from ten years ago. Removing old nullifiers would allow those notes to be spent again. Forcing old notes to move before a deadline would strand the funds of anyone who missed it. Bowe and Miers state the same dilemma in their note on this problem.

The commitment tree also grows, but it causes less trouble. Tachyon's deep dive draws the distinction this way. Commitments can sit on disk, while every incoming transaction must check its nullifiers against the entire set. That pushes validators to hold the set in memory on the path that decides whether a transaction is valid. So the nullifier set is the state that limits throughput.

The growth itself is plain arithmetic. Take a hypothetical load of one hundred transactions per second, each with two spends and two outputs. These inputs are illustrative and do not forecast anything. Each spend adds one nullifier of thirty-two bytes, so the set grows by two hundred nullifiers per second. Counting only the raw bytes, that reaches two hundred one point eight gigabytes after one year and one thousand nine point two gigabytes after five years. This growth has no ceiling, because no entry ever leaves the set.

The deep dive quotes a far larger figure from a talk, five hundred gigabytes per day at Visa-level throughput. We have not checked its assumptions, which the book does not spell out, but the shape of the problem is the same at any rate. A validator's cost depends on the entire history of the pool, so faster hardware only postpones the limit.

Faster block validation alone would not change this either. Even if verifying proofs became free, the set would keep growing with each spend. This is why a post in the forum thread on Tachyon and Ragu describes validator state, rather than verification speed, as the main target.

Why wallets download everything.

The second cost falls on recipients. A sender creates a note, but the recipient must learn the note's contents in order to spend it, and that includes the random values. The two parties may have no private channel, so Zcash has always used the chain as a public bulletin board. The sender encrypts the note to the recipient's address and publishes the ciphertext inside the action. This is called in-band secret distribution.

Encryption hides the recipient from everyone, including the recipient's own wallet, which has no way to tell which ciphertexts are addressed to it. Nothing public can reveal this, because any public marker of the recipient would link payments together. So the wallet attempts to decrypt every output on the chain with its viewing key, and it keeps those that succeed. This is trial decryption. Its cost grows with the total traffic on the chain, regardless of how many payments the wallet receives.

A full node could absorb this as computation, but a phone also has to download the data. ZIP three oh seven reduces the download by sending a compact form of each output. A wallet also wants each nullifier, so that it can tell when its notes have been spent. Together these come to one hundred forty-eight bytes per action, compared with eight hundred twenty for the full action.

At the same hypothetical load there are two hundred actions per second, so a wallet attempts seventeen million two hundred eighty thousand trial decryptions per day, whether or not anyone has paid it. Even the compact form costs two point six gigabytes per day, and a wallet that comes back after thirty days offline faces seventy-six point seven gigabytes.

This cost has already caused real trouble at far lower volume. After the N U five upgrade in twenty twenty-two, shielded outputs rose from a monthly average of forty-two thousand six hundred to twenty-one million six hundred twenty-two thousand five hundred ninety in June, in an episode known as sandblasting. Some mobile wallets could no longer sync in a reasonable time, and some users could not reach their funds. The fee changes and wallet improvements that followed reduced the damage, but they did not remove the underlying link between chain traffic and wallet work.

A linear scan also has a privacy cost. The deep dive notes that it leaks metadata, and that it becomes infeasible for mobile wallets with limited bandwidth as throughput rises.

Tachyon's approach in outline.

We now have both costs in front of us, and they share a structure. In each case, a party does work proportional to everybody's activity in order to answer a question about one note. A validator searches all of history to ask whether this note has already been spent. A wallet reads all of history to ask whether a given output belongs to it.

Tachyon's guiding principle, which the deep dive calls client-side validation, is to move as much of this work as possible away from consensus and onto the party that cares about the answer. That party then supplies a proof, which validators can check cheaply.

Tachyon applies the principle in three ways, and the next sections take them in turn. First, note delivery leaves the core shielded protocol, so that wallets no longer scan every ciphertext to find their notes. Second, nullifiers change over time, so that validators can forget old ones, and the spender proves that none of the note's nullifiers appeared in the part of history validators have forgotten. Third, many transactions share one proof through aggregation, which reduces the chain space and verification time per transaction. The second and third rely on proofs that can absorb other proofs, and the end of this chapter collects what this demands from the proof system.

Separating note delivery from the protocol.

Orchard's payment address carries two responsibilities. It says who owns a note, and it also provides the key that encrypts the note to its recipient. The deep dive separates these into two layers. The shielded protocol only tracks notes and enforces who may spend them. A payment protocol run by wallets decides how a sender gets the note's contents to the recipient.

The note format reflects the split. A Tachyon note drops the address and rho, and it keeps only what ownership and uniqueness need. Those are a payment key, the value, psi, and r c m. The payment key is a commitment to the owner's authorization key and nullifier key. The key that encrypts a note no longer appears in the note at all. The chapter on notes and nullifiers covers these keys.

Once delivery is a separate layer, wallets can use channels other than the chain. A web checkout, a payment terminal, or a messaging app can carry the note's contents directly, as Sean Bowe's original post proposes. The wallet then learns of a payment without scanning anything. This is out-of-band delivery, and it is the source of the common summary that Tachyon removes in-band secret distribution.

The current design is less absolute than that summary, because the sources differ on how far delivery leaves the chain. Bowe's posts describe fully out-of-band payments, and so does the Tachyon book's key hierarchy page, which carries a note saying it is significantly outdated. The deep dive instead sketches a design from a separate team, in which the address travels out of band while encrypted memos remain on chain with a short tag for each note.

Wallets in that design fetch their memos by tag through private information retrieval, which lets a client read a database entry without the server learning which one. A key-exchange ciphertext appears on chain only for a first contact. Meanwhile the bundle format and the code both carry one optional, opaque memo per bundle, and the deep dive says the shielded protocol never parses it.

This site follows the code on this point. The shielded protocol leaves a place for opaque payload data and does not depend on it. How wallets use that field is a payment-protocol choice that is not settled.

In either version, the protocol no longer requires every action to carry a ciphertext that every wallet must try, and this step breaks the link between chain traffic and wallet work. The change has costs of its own. The chain stops being a complete record from which a seed phrase can recover everything, so the deep dive sketches periodic encrypted backups of wallet state on chain. Addresses in that sketch also become harder to share, because the post-quantum encryption keys are too large for a Q R code. A post in the forum thread names the user experience of removing in-band delivery as a pressing concern.

Evolving nullifiers.

We now turn to the validator's problem. Consider the most direct way to let validators forget old nullifiers. Validators keep only the nullifiers from recent blocks, and a spender adds a proof that the note's nullifier does not appear anywhere in the older history. We call this an exclusion proof. Validators check the recent part themselves and rely on the proof for the rest, so their state no longer depends on the age of the chain.

This idea has two practical problems. First, the exclusion proof must stay current as new blocks arrive, and a wallet that is offline or running on a phone cannot do that work continuously. It could hire a service to do it, but that leads to the second problem. To test a nullifier against history, the service must know the nullifier. When the note is eventually spent, that same value appears on chain, so the service learns exactly when its client spent the note.

The fix is to stop giving each note a single nullifier. Tachyon divides time into epochs and gives a note a different nullifier in each epoch. A wallet can then hand a service the nullifiers for past epochs, while the value revealed at spend time belongs to a later epoch and looks unrelated to anything the service saw.

Here is how the nullifiers are defined. Each note has its own master key, which is the Poseidon hash of psi and the nullifier key. The nullifier for a given epoch is a pseudorandom function of the epoch number, keyed by that master key. Poseidon is a hash designed to be cheap inside proofs, and the chapter on statements and challenges returns to it.

Only the holder of the nullifier key can compute the master key, and a pseudorandom function's outputs reveal nothing about one another. So the value at one epoch tells a service nothing about the value at any other epoch.

This breaks a rule that every earlier Zcash pool relies on, namely that a note has exactly one nullifier. A set of past nullifiers can no longer catch a double spend by looking for a repeat, because a second spend in a later epoch publishes a different value. So Tachyon needs a new double-spend rule as well.

One caution about epoch length, because the sources give different values. The code sets an epoch to four thousand ninety-six blocks outside its test configuration, which at the current seventy-five second block target is about three point five six days. The book's examples use one day in the nullifier analysis and two weeks in the deep dive. This site follows the code.

Catching double spends without full history.

The new rule splits the check between the spender and the validators. A spender chooses a target epoch and must satisfy two conditions.

The first condition is the exclusion proof. For every closed epoch from the note's creation up to the one before the target, the proof shows that the note's nullifier for that epoch does not appear anywhere in that epoch's published data. Each nullifier is tested only against its own epoch, so the work is one test per epoch. A note spent in the same epoch it was created has no closed epochs to cover and skips this step.

The second condition is a check by validators, who retain every published value from the current and preceding epochs. A spend must publish its nullifier for the target epoch, and validators reject it if any published value matches a retained one.

A timing problem forces one more detail. A transaction built for one epoch may still be waiting to be mined when the next epoch begins, and neither miners nor the syncing service can update the proof on the wallet's behalf. So Tachyon accepts a spend during its target epoch and the following one. This grace period would open a gap on its own, so each spend publishes two nullifiers, the one for the target epoch and the one for the epoch after it.

Picture a note created in epoch three and spent with target epoch seven. The exclusion proof covers epochs three to six, showing that each epoch's own nullifier is absent. Validators retain epochs six and seven and have pruned the earlier ones. The spend publishes the nullifiers for epochs seven and eight.

Now suppose the owner of a note tries to spend it twice, and call the spend that the chain accepts first the first spend. The proof pins each published nullifier to the note and the epoch, so the owner cannot disguise the second spend by publishing fresh values. The owner can only choose the second spend's target epoch and when to submit it.

The argument depends on what the pair of nullifiers guarantees. A spend lands in its target epoch or the next one, and it publishes the nullifiers of both. So it always publishes the nullifier of the epoch that accepts it. We'll call the epoch that accepted the first spend the accepting epoch, and its nullifier now sits in that epoch's data. The second spend's target is either later than the accepting epoch or not, and each case fails for a different reason.

Suppose the target is later than the accepting epoch. Then the exclusion proof must cover the accepting epoch, because it covers every closed epoch before the target. The proof would have to show that the accepting epoch's nullifier is absent from that epoch's data. That is false, so the owner cannot produce the proof.

Now suppose the target is not later than the accepting epoch. The exclusion proof stops short, so the validators have to catch the spend. The second spend lands in the accepting epoch or later, and a spend lands at most one epoch after its target. So its target is either the accepting epoch or the one just before it, and both give a pair that includes the accepting epoch's nullifier. The spend also lands in the accepting epoch or the one after it. Validators still retain the accepting epoch at either point, so they find the repeated value and reject the spend.

Let's run this on our note. Suppose its first spend targets epoch seven and lands in epoch eight. It publishes the nullifiers for epochs seven and eight, so epoch eight is the accepting epoch. A second spend targeting epoch seven publishes those same two values, and a second spend targeting epoch eight publishes the nullifiers for epochs eight and nine. Either way, it repeats the nullifier for epoch eight, and the validators still hold that value, so they reject it. A second spend targeting epoch nine publishes fresh values, but now its exclusion proof would have to show that the nullifier for epoch eight is absent from epoch eight, and the owner cannot produce that. Any later target fails in the same way.

This argument assumes that the proofs cannot be forged and that the pseudorandom function behaves as one. The chapters on notes and nullifiers and on pool state give the full treatment, including how a proof can refer to history that validators no longer hold.

What validators store now.

Tachyon also simplifies what gets stored. Every published value, whether a nullifier or a note commitment, is a thirty-two byte tachygram, and consensus treats all of them identically. So that observers cannot tell spends from outputs, each action publishes exactly two tachygrams. A spend publishes its two nullifiers, and an output publishes its commitment and a padding value. Each bundle adds one more tachygram for a fee change note, as the code's error message also states.

The window that validators retain is therefore bounded by throughput and epoch length, and the chain's age does not enter into it. Validators can prune older tachygrams.

Return once more to the hypothetical one hundred transactions per second. A Tachyon action is either a spend or an output, so each transaction has four actions and publishes nine tachygrams, two per action plus one. The window holds at most two epochs of these, which is six hundred fourteen thousand four hundred seconds of traffic, and at its peak that is seventeen point seven gigabytes.

Compare that with the Orchard-style nullifier set at the same load. For the first thirty-two days or so the window is the larger of the two, because it records more values per transaction. After that the nullifier set keeps growing while the window stays where it is.

The size of the window depends on the epoch length, which is not settled. The book's one-day epoch gives a peak of five point zero gigabytes, and its two-week epoch gives sixty-nine point seven.

The comparison matters for the shape of the two curves. The window is not small at this load, but it stops growing. Doubling the throughput doubles the window, which is a cost a validator can plan for. In the nullifier set, the same doubling steepens a line that never levels off.

Validators do not forget everything. They still keep the anchor chain, a hash chain over the pool's history that lets them check that a proof refers to a real point in the chain. In Tachyon an anchor is a state of this hash chain, which differs from the Merkle root we met in Orchard. The chain advances once per stamp, where a stamp is the part of a bundle that holds its proof and tachygrams. So the chain grows with the number of stamps rather than with the number of notes.

Someone must also keep the pruned data, or nobody could build exclusion proofs against it. A post in the forum thread acknowledges that this leaves a data availability problem, and we treat the question of who stores old history as unsettled.

The data on the chain.

The next sections refer to an epoch's history, so we should say what that history consists of. A block holds transactions, and the Tachyon part of a transaction is a bundle. The bundle format divides a bundle into a body and a stamp, and validators use each part differently.

The body holds the net value balance, each action's value commitment and randomized signing key, the signatures, and an optional memo. Validators use it to check the signatures and the value balance. The stamp holds the tachygram list, the anchor, the proof, and a few values that go with them. Validators verify the proof, compare the tachygrams against the window, and advance the anchor chain.

Unlike an Orchard action, a Tachyon action carries no note ciphertext. Nothing in the bundle names a note or its owner, and the tachygrams carry no labels saying which kind each one is.

A transaction can also give up its stamp and point to another transaction's stamp, whose list then includes its tachygrams. An epoch's history is therefore the tachygram lists of all the stamps in that epoch's blocks. Validators hold this data for two epochs and then prune it, and the service in the next section has to read it.

Outsourcing the exclusion proof.

Exclusion proofs still require someone to read every tachygram of each epoch being tested. Tachyon lets a wallet delegate this reading to an oblivious syncing service, which is untrusted and sees very little.

The service receives opaque pairs, each made of an epoch number and a value. For each pair, it proves that the value is absent from that epoch's history, and it returns the proof. It never learns the note or its commitment, and it cannot compute any nullifier beyond the list it was given. Nothing even shows that the values come from a real note, so a wallet can mix in decoys. Once the proof returns, the wallet separately proves that the values the service tested are the nullifiers of its note. This second step attaches the anonymous work to a real note, and it needs the note's secrets, so the wallet performs it.

Each epoch's nullifier is unrelated to the others, so the two values that later appear on chain at the spend lie outside the delegated list, and the service cannot recognize them. This assumes that the wallet does not delegate those epochs and that the master key stays secret. Requests from one wallet could still be correlated with each other, and the sources suggest mixnets, standard request shapes, and decoys. The chapter on oblivious sync covers how the service proves absence over a whole epoch.

So an older note's path runs from the wallet to the service and back, with proofs of absence. The wallet then binds those values to the note, builds its transaction proof, and sends the result toward an aggregator and finally the validators.

Aggregation.

So far, every transaction carries its own proof, and an Orchard proof is the largest part of an Orchard transaction. Aggregation addresses this. An aggregator takes the stamps of several transactions and merges their proofs into one that covers all of them. We use the word merge as the Tachyon book does, and the Ragu book and code call the same two-into-one operation fuse. The original transactions go into the block without their proofs and point to the aggregate instead. Miners are likely to take on this role. Validators still check each transaction's signatures and value balance, and they check every tachygram against the window, but they verify only one proof.

Here is what that does to the on-chain bytes of a transaction with two spends and two outputs, leaving out small fields that are similar in each.

Orchard's total is nine thousand thirty-two bytes, of which the proof takes seven thousand two hundred sixty-four. Tachyon's total is eight hundred thirty-two bytes, made up of action descriptions, signatures, tachygrams, and a maximum fee commitment, plus a share of one aggregate proof.

These totals also show how far the hypothetical load is from today's chain. At seventy-five seconds per block, it needs about sixty-seven point seven megabytes per block with Orchard and six point two four megabytes with Tachyon, before counting the aggregate proof. Both exceed the current limit of two megabytes per block, so this load would also require a larger block limit. Keeping the block history at this load would add about two point six terabytes per year for Tachyon, excluding proofs.

This comparison is not exact. The Orchard figure includes encrypted memos, while the Tachyon figure leaves out its optional memo field, the reference to the aggregate, and the aggregate proof, whose real size is not settled. The chapter on aggregation and bundles explains why the mock's placeholder probably overstates the proof's share. The largest part of the savings comes from removing the per-transaction proof.

Verification time follows a similar pattern, though aggregation does not win in every case. The Ragu book's rough estimate puts an aggregate's verification at about one hundred milliseconds, with the break-even against Orchard's batch verification near fifty transactions. The book marks these as estimates still to be validated with benchmarks. One aggregate costs more to verify than one Orchard proof, and it pays for itself as the number of transactions grows.

Who reads what.

All the participants have now appeared, so we can say what each one reads and what it can ignore. This map is reconstructed from the book and code at the commit this site pins, and the authors have not confirmed it. The book's network roles page names the mempool, aggregator, and miner, and the deep dive adds the sync service. The archive is our own label for a role that nobody has been assigned yet.

A wallet reads its note's contents from the sender and the service's absence proofs, and it can ignore other people's notes and the tachygrams of the epochs it delegates. The sync service reads every tachygram of each epoch it tests, and it can ignore the note, its commitment, and the wallet's keys. An aggregator can ignore epochs older than the ones its working aggregate depends on. Miners and validators hold the window and the anchor chain, so they can ignore older tachygrams. The archive reads every stamp so that old epochs stay available, and it cannot read the contents of notes.

Parts of this picture are less settled than that list makes them sound. The proof tree needs the wallet to hold the data of its note's creation stamp, but the sources we read do not say how a wallet finds that stamp or fetches it privately. We also found no description of where the sync service gets old epochs, which is the data availability question from earlier.

What this requires from a proof system.

Tachyon now places a specific set of demands on its proof system, and these demands explain much of Ragu's design.

First, proofs must absorb other proofs. An exclusion proof has to extend from epoch to epoch without being rebuilt from scratch, and without handing the verifier a list that grows with the note's age. Aggregation has to turn two proofs into one. In both cases, a new proof must establish that an earlier proof was valid, and then add something. A proof of this kind is recursive, because the statement it proves includes running the verifier of another proof. The general form of this idea, in which a whole tree of computation steps carries proofs along its edges, is called proof-carrying data, and the next chapter introduces it.

Second, proofs must be small, because stamps travel through the network and are stored on the chain. The Ragu book gives this requirement as the reason for building on the elliptic curve discrete logarithm. Given the current state of the art, it says, small recursive proofs essentially limit the design to constructions based on that assumption. It aims for performance comparable to the proofs Orchard already deploys.

Third, there should be no trusted setup. Some proof systems depend on public parameters generated from a secret, and anyone who kept that secret could forge proofs. Zcash's Sprout and Sapling pools used such parameters, and Orchard removed the need for them by moving to Halo two. The Ragu book describes a strong desire to keep it that way, which limits it to polynomial commitments based on the inner product argument from Bulletproofs.

These last two requirements pull against each other, and that tension sets the main technical problem of the site. Verifying an inner product argument takes group operations in proportion to the size of the committed vector. A recursive proof would have to carry out that verification inside itself at every step. The way out, from the Halo paper, is to defer the expensive check from one proof to the next and merge the deferred checks as they accumulate, which the chapter on accumulation develops.

Ragu also keeps the committed vectors small, with a preferred size of two to the eleven multiplication gates per step. A single step therefore does little work. Tachyon's analysis counts a capacity of seven Poseidon permutations per step, so a large statement must be split across many small steps.

Fourth, the curves should be the Pasta cycle. Orchard already uses the Pasta curves, Pallas and Vesta. Spend authorization in Orchard, and in Tachyon, is a Red Pallas signature over Pallas, and hardware wallets already sign on these curves. The Ragu book names this deployed base as a reason for preferring them. They also suit recursion for a structural reason, which is that the two curves form a cycle in which each curve's scalar field is the other's coordinate field. The chapter on curve cycles explains why that matters.

These choices come at a cost, and the cost is post-quantum soundness. A large enough quantum computer could forge discrete-log proofs. Tachyon's stated goal is privacy that resists a future quantum computer from the start, with soundness left for a later upgrade to a lattice-based scheme. The deep dive says that the details of that upgrade remain to be determined.

Where this leaves us.

Let's collect what we've covered. Shielded notes appear on chain only as commitments, and validators test each spend's nullifier against a set that can never shrink, because notes never expire. Notes also travel as ciphertexts that no public marker can identify, so wallets must trial-decrypt all traffic.

Tachyon moves note delivery out of the shielded protocol, although how much payload remains on chain is not settled. Nullifiers change each epoch, a spender proves that its nullifiers are absent from closed epochs, and validators retain only two epochs of tachygrams, so their window stops growing. An untrusted service can do most of the exclusion work without learning which note it serves, and aggregation merges the proofs of many transactions into one.

These ideas need small recursive proofs, with no trusted setup, on curves that Zcash already deploys. Tachyon itself is still a proposal, and none of this has activated on mainnet.

The requirement that proofs absorb other proofs is the one that shapes everything else. The next chapter, An Introduction to Proof-Carrying Data, states that goal precisely before any machinery appears, using Tachyon's aggregation as its running example.
