Chapter nineteen. Notes, nullifiers, and tachygrams.

The earlier parts of this site built a proof system that can absorb other proofs. This chapter returns to the application that system serves. The opening chapter on scaling Zcash described Tachyon in outline, with epochs, evolving nullifiers, and a window of retained values. Here we work out the objects themselves. We cover which keys a wallet holds, what a note contains, and how a wallet derives a note's nullifiers for each epoch. We also cover why a spend publishes two of them, and why every action publishes exactly two values of a single kind.

We do not cover how a proof refers to the pool's history or how a spender shows absence from old epochs. The next chapter builds the pool state, the chapter on oblivious sync covers absence proofs, and the chapter on the proof tree walks through the steps that prove all of this.

A caution about the status of these designs. Tachyon has not activated on mainnet and its design is still changing. Everything here describes the Tachyon repository at the commit this site pins, whose shielded protocol specification is still an empty outline. The book's own key hierarchy page carries a note calling itself significantly outdated, and the book's analysis of nullifiers presents its choice as a recommendation with an alternative. Where the sources differ, we give both and follow the code unless we say otherwise. Tachyon also pins a different revision of Ragu from the one the earlier chapters read.

Fields and stand-ins.

Tachyon's objects live in two fields. Pallas, the curve used for spend authorization, has coordinates in one field and scalars in another. Poseidon's inputs and outputs, and therefore all tachygrams, are elements of the coordinate field, and signing keys are elements of the scalar field. The toy curve has the same shape, with coordinates modulo thirty-one and scalars modulo forty-three, so we use it for every signing key below.

The hashes need a different treatment. Tachyon uses Poseidon throughout, and each use has its own domain. In a field of thirty-one elements, unrelated hash outputs would collide constantly, and that would hide the behaviour we want to see. So the examples use a stand-in, which is SHA two fifty-six of a tag and the inputs, reduced modulo sixty-five thousand five hundred thirty-seven. These numbers are not Poseidon outputs and are not elements of the toy field. They only show the structure, and the small range is useful later, because it lets us count a cheater's chances exhaustively.

The spending key and its two children.

Spending a note requires two separate abilities. The owner has to authorize the spend with a signature, and the owner has to produce the note's nullifiers, which nobody else should be able to compute. The book's deep dive observes that these are the only two abilities the shielded protocol needs from its keys. Everything else in Orchard's key tree, including viewing keys and diversified addresses, supports delivering notes to recipients and detecting them, and delivery has moved to a separate payment protocol.

The root is a spending key of thirty-two random bytes, and each ability gets one child derived from it. The two derivations differ only in a one-byte domain, through BLAKE two b with the Zcash expansion personalization. The first child is the spend authorizing key, a scalar, and its public point is the spend validating key. The second child is the nullifier key, an element of the coordinate field, and it has no public counterpart.

One detail comes from RedPallas, the signature scheme that Orchard and Tachyon share. It requires the spend validating key to have a cleared sign bit in its compressed encoding. A point and its negative have the same x coordinate and opposite signs of y. So if the derived point has the wrong sign, the code negates the spend authorizing key, which negates the point. On the toy curve we use the parity of y as the sign.

Take Alice's wallet, whose spending key is a short text standing in for random bytes. Expanding it gives the scalar nineteen, whose public point has an odd y coordinate. So the wallet negates the scalar, giving twenty-four modulo forty-three, and its public point now has an even y coordinate.

Proofs do not check these derivations from the spending key. The deep dive says that the circuits use the spend validating key and the nullifier key as witnesses and never constrain how they arose. A wallet standard chooses the path, and the protocol only needs the results to look like randomly sampled keys.

The payment key.

A sender has to name the owner of a new note. Publishing the two keys to the sender would give away the nullifier key, so the note carries a commitment to the pair. The payment key is a Poseidon hash of the two coordinates of the spend validating key together with the nullifier key. If the same wallet walks to the next index for a second sender, it obtains different keys and an unrelated payment key, and nothing in the two payment keys shows that they belong to one wallet.

Two facts about this hash shape the rest of the design. First, the payment key is a deterministic function of the pair, so one payment key handed to two senders would let them compare notes and link the payments. A hash admits no tweak, so unlinkability comes from minting a fresh address per sender. The index that makes keys differ sits above the spending key, which is why our second address started from a second seed.

The book gives two reasons for preferring a hash over Orchard's diversified base. That trick has no known secure analogue under lattice assumptions, and handing the spend validating key to senders would let one who kept it attack it later with a quantum computer.

Second, the hash binds the nullifier key to the note's owner field, and we'll soon see that this is what stops a spender from inventing a second nullifier sequence.

The wallet can also separate proving from signing. The proof authorizing key is the pair of the spend validating key and the nullifier key. It gives a device what it needs to build proofs for every note paid to the matching payment key, and it cannot sign. So a hardware wallet can hold the spend authorizing key while another device does the proving.

The key hierarchy page and a code comment call the nullifier key wallet-wide, so that one proof authorizing key covers all of a wallet's notes. That does not fit a fresh pair of keys per sender, and the sources do not reconcile the two. On the per-sender reading, the nullifier key computes nullifiers given a note's trapdoor, and so sees when the note is spent, while the payment key only receives notes.

The book and the code differ on narrower delegation. The key hierarchy page, marked as outdated, lists a per-note bundle built from the note's master key, which we'll meet shortly, so that a prover could work on one note only. The code, at the commit this site pins, has two steps that witness a full proof authorizing key, so a prover holding only that bundle could not run them. A comment on the type says that proof delegation is yet to be specified. This site follows the code, and treats per-note proving delegation as unsettled. A sync service, by contrast, receives only values and no key material.

Notes and commitments.

A note has to record who owns it and what it is worth, and it needs enough randomness to stay hidden and to have nullifiers of its own. Tachyon's note has exactly four fields. They are the payment key, a value in zatoshi between zero and two point one times ten to the fifteen, a nullifier trapdoor, and a commitment trapdoor. The nullifier trapdoor gives the note its identity for nullifier derivation, and the commitment trapdoor hides the note inside its commitment. Compared with Orchard's note, the diversifier and transmission key have become the payment key, and the field called rho has gone. We'll return to what removing rho costs.

The sender chooses both trapdoors and so knows all four fields, as the threat model assumes. The recipient has to learn them as well, through whatever payment protocol the two wallets use. How to generate them is unsettled. The deep dive says they should come from a standardized derivation off a wallet key, the code comments say they can come from a key negotiated out of band, and we found no standard at this commit.

Suppose Bob pays Alice twenty-five zatoshi using her payment key. Bob cannot publish the note's fields, so he publishes a note commitment that fixes all four, which is a Poseidon hash of the commitment trapdoor, the payment key, the value, and the nullifier trapdoor.

Sapling and Orchard use variants of the Pedersen commitment, which rely on discrete log, and Tachyon uses a hash alone. Each Tachyon use of Poseidon starts its sponge with a zero rate and with the domain name as a number in the capacity cell. So different domains behave as unrelated hash functions, even on identical inputs, and the padding tachygram later relies on this.

In our stand-in, changing only the commitment trapdoor gives a commitment that looks unrelated to the first, although the note has the same owner, value, and nullifier trapdoor. A random commitment trapdoor is what lets the commitment hide two notes with the same owner and value from each other, and hiding here assumes that Poseidon behaves like a pseudorandom function.

Randomizing the signing key for each action.

Everyone has to be able to check a signature, so its verification key must be public. If that key were the spend validating key, every spend under that key would carry the same public key, and an observer could link them all. So spend authorization works as in Orchard. Each action picks a scalar, called alpha, and signs with a randomized key, which is the spend authorizing key plus alpha. The public version of this key is the spend validating key plus alpha times the generator.

Scalar multiplication distributes over addition, so that point is exactly the public key of the randomized signing key. The action publishes the randomized public key, and the proof shows that it came from the spend validating key inside the note's payment key.

Tachyon derives alpha from per-action entropy and the note commitment, with a Poseidon hash read as a scalar, which is possible because the coordinate field is smaller than the scalar field. This ties the key to the note, and it lets a signing device recompute alpha from the note and the entropy without having to trust a value handed to it. Our stand-in output is far larger than forty-three, so here we reduce it modulo forty-three, which the real construction does not do. In our run alpha is twenty-three, so the randomized signing key is twenty-four plus twenty-three, which is four modulo forty-three. The script confirms that four times the generator equals the published point.

A signature follows the Schnorr pattern. With a nonce of nine, the signer computes the nonce's point and derives a challenge of eighteen from a hash of that point, the randomized key, and the message. It returns nine plus eighteen times four, which is thirty-eight modulo forty-three. The verifier checks that thirty-eight times the generator equals the nonce's point plus eighteen times the randomized key. The verifier never used the spend validating key.

The published key reveals nothing about the spend validating key when alpha is uniform, because adding a uniform multiple of the generator produces a uniform point whatever the starting key. We can test this exhaustively on the toy curve. Of the forty-two points other than the identity, twenty-one have an even y coordinate and could be a normalized key. For each of those twenty-one candidates, exactly one alpha turns it into the published point. So the published key is equally consistent with every owner, and a second action by Alice publishes an unrelated-looking point.

An output action has nothing to authorize, since creating a note spends nobody's money. It still has to look like a spend, so it also publishes a key and a signature, with the signing key equal to alpha alone, using the domain Tachyon Output in place of Tachyon Spend. Both shapes produce a uniform point. Each action also publishes a value commitment, which the chapter on the proof tree covers.

Deriving a note's nullifiers.

The opening chapter set out what an epoch nullifier has to do. A note needs a different nullifier in each epoch, these values must look unrelated to anyone without the owner's secret, and each epoch must have exactly one valid value. A wallet might also need many of them at once, because a proof about an old note covers every epoch since its creation. These needs lead to a derivation in two stages.

The first stage combines the two secrets that make a nullifier belong to this owner and this note. It hashes the nullifier trapdoor and the nullifier key to produce the note's master key. The sender knows the trapdoor and not the nullifier key, and the wallet holds the nullifier key for many notes, so only the owner of this specific note has both. Doing this once also keeps the nullifier key out of later headers. In the proof tree, a step called note seed computes the master key and passes it on, and no later header carries the nullifier key. However, the spend action step witnesses the proof authorizing key again to check the payment key.

The second stage turns the master key and an epoch into nullifiers. One Poseidon permutation yields a whole rate's worth of output, so four values cost the same as one. Wasting three of them would be a poor use of a limited circuit, so Tachyon takes all four and assigns them to four consecutive epochs. To find the value for an epoch, round the epoch down to the start of its group of four, and run one sponge over the master key and that group start. Then take the entry at the epoch's position in the group. For epoch seven, the group starts at four, and the nullifier is the entry at position three.

Here is the running note's sequence, created in epoch three and spent with target epoch seven. We use target epoch for the epoch that a spend's proof reaches, and the sources also call it the anchor's epoch or the present epoch. The nullifiers for epochs zero to two come from before the note existed, and they play no part. The nullifiers for epochs three to six get tested for absence. The nullifiers for epochs seven and eight get published by the spend. Those for later epochs are never revealed.

A value depends only on the master key and the epoch, because each group absorbs its own start. So two derivations that overlap agree on the epochs they share, and the script asserts this for our note.

Both inputs matter. A second note to Alice, with a different trapdoor, has a different master key and different nullifiers, so her two notes do not share them. Bob knows the first note's trapdoor, but his own nullifier key gives a different master key, and a nullifier for epoch seven that differs from the true one. So the sender of a note cannot watch for its spend.

The privacy argument assumes that Poseidon, keyed by the master key, behaves as a pseudorandom function. Revealing some outputs then says nothing about the others, including the pair revealed at spend time. The code allows epoch indices up to one million forty-eight thousand five hundred seventy-five, since a block height has thirty-two bits and an epoch has four thousand ninety-six blocks. At seventy-five seconds per block, that range lasts about ten thousand two hundred seven years.

The sources differ on the nullifier's inputs. The deep dive hashes the nullifier key and then the trapdoor, and it absorbs the epoch divided by the rate and rounded down, calling this the leading candidate. The nullifier page and the code, at the commit this site pins, have the master key absorb the trapdoor first, and the sponge absorbs the group-aligned epoch. For epoch six, the deep dive absorbs one while the code absorbs four. In our stand-in the two choices give different values, so they are different functions, although each gives every epoch one fixed value.

This site follows the code. Comments in the code also lag behind it.

Why the wallet derives its own nullifiers.

A reader might expect a design in which the wallet hands a sync service a key for a range of epochs, and the service computes the nullifiers itself. An earlier Tachyon design did this, and the book keeps it as an archived page. Proof cost is the reason it was replaced, and a comparison makes that concrete.

The archived design used the GGM construction, which treats an epoch's bits as directions down a binary tree. A seed sits at the root, each node has two children given by two hashes, and each leaf is a nullifier. Hashes are one-way, so holding a node gives access to the leaves below it and to nothing else, which is exactly a key for a range of epochs.

Take a space of eight epochs. To delegate epochs two and three, a wallet hands over only the one node above them, and one-way hashing keeps the holder away from all the other nullifiers. The range of epochs zero to six needs three such nodes, and the worst case in this small space needs four, so the amount of delegated key material depends on the range.

The trouble is that each level of the tree costs one hash inside a proof, and proof steps are small. A step has two thousand forty-eight multiplication gates, and one Poseidon permutation costs two hundred eighty-eight of them, so a step fits seven permutations. A binary tree over an epoch space of two to the fourteen days, about forty-five years, has depth fourteen, so one walk takes fourteen permutations and overflows a step. A tree with higher arity near the root can cut the depth to seven, which just fits one walk.

The analysis wants at least two nullifiers in one step, since a spend publishes two, and a tree walk cannot provide that. It then tries other constructions and recommends using a Poseidon permutation directly, with its output of four values. The analysis calls this attempt three, and it is the design we just described. With one hash per nullifier, a step yields seven nullifiers. With four values per permutation, a step yields seven times four, or twenty-eight.

This construction gives up the range key, because a plain hash has no partial key to hand out. So wallets derive and prove their own nullifiers, and they send the service explicit values. The service then holds a finite list and can compute nothing beyond it, and the chapter on oblivious sync shows how the wallet later ties the service's work to its note.

The analysis and the code differ on nullifiers per step. The analysis page gives twenty-eight derivations per step, and its conclusion offers a MiMC-based alternative at about fifty to sixty-eight per step, for those willing to accept the added dependency. In the code at the commit this site pins, the derivation width is sixteen, so the nullifier derive step runs four sponges per window, and the step also binds the window to a committed sequence. The sources do not explain the choice of sixteen. This site follows the code, and treats twenty-eight as the analysis's upper count.

How the commitment pins the nullifiers.

Publishing a nullifier only prevents double spends if a spender has no choice about its value. If a spender could produce two nullifier sequences for one note, the second sequence would pass both the exclusion proof and the window, since neither has ever seen those values. The note commitment has to rule this out, and it does so through a chain of hashes.

Follow the chain from the top. The spend validating key and the nullifier key feed the payment key. The payment key, the value, and the two trapdoors feed the note commitment. Separately, the nullifier trapdoor and the nullifier key feed the master key, and the master key gives the nullifier at each epoch. So the nullifier trapdoor and the nullifier key, the two inputs to the master key, both sit behind the note commitment.

The proof's note seed step computes the payment key from the witnessed proof authorizing key, builds the note, and derives both the master key and the commitment from the same trapdoor and nullifier key. A seed can name any note it likes, so this step alone proves little. The claim closes later, when a step called spendable init requires the commitment to be a member of a creation stamp's tachygrams. So the spender is held to a commitment that already exists in the pool.

To cheat, a spender would keep the commitment fixed while changing what lies behind it. Our small hash range allows us to try every possible change to one field at a time. One wrong nullifier key and one wrong nullifier trapdoor keep the commitment the same, and either would give the cheater a second nullifier sequence. Two wrong values also match, which would give a different value for the same note, and two wrong commitment trapdoors match, which gives nothing useful.

A random function into that range should produce about one match per field, and each of these six is a real collision. For one wrong nullifier key, the payment key comes out the same, so the commitment stays the same, while the master key and the epoch seven nullifier both change. On this toy scale a cheater could double spend.

The attack succeeds here only because the range is small. The protection comes entirely from the assumption that nobody can find such a collision, so it needs a hash with a far larger range. Real Poseidon outputs have about two hundred fifty-five bits, and a search of the kind we just ran would be hopeless. Two further assumptions complete the argument. The proof system must not allow a false statement to verify, and the proof must really compute these hashes. We qualify that last assumption near the end of this chapter, since these steps do not yet run as real circuits.

The remaining pieces follow the same pattern. The spend bind step computes the published pair from the threaded master key and the epoch, so no nullifier is a free witness. It also compares the secret's commitment with the one the spendable lineage carries, and the book's proof tree page notes what this rejects. A phantom note that reuses the nullifier trapdoor with a larger value has a different commitment, and nobody ever published that commitment.

Reusing a trapdoor.

Nothing in the protocol forces the nullifier trapdoor to be unique, because the pool holds an unordered set of values and gives notes no position to bind to. Orchard avoided this by setting a new note's rho to the nullifier of a spent note, and consensus already forbids repeated nullifiers. Tachyon cannot enforce that binding, and a malicious sender can exploit this.

Suppose Bob sends Alice a second note with value nine, a new commitment trapdoor, and the same nullifier trapdoor. Its commitment differs from the first, so it looks like a separate note. But the payment key fixes the same nullifier key, so both notes have the same master key and the same nullifier at every epoch. Once Alice spends one of them, the other can never be spent, because its nullifiers have already been published. A wallet detects this on receipt by computing one nullifier at a fixed reference epoch for each incoming note. With reference epoch zero, both notes give the same value, and the wallet rejects the second.

This is the faerie gold attack, in which a recipient holds money that turns out not to be spendable. It harms the recipient and creates no money, and Tachyon moves the defence out of consensus. A wallet's own note set is small, which keeps the comparison cheap.

The sources differ on this attack too. The deep dive says it remains possible in principle, and that resisting it becomes the responsibility of the payment protocol, through the wallet check we just described. The code comments at the commit this site pins call the attack moot under out-of-band payments, and say that nullifiers need no collision resistance. The nullifier page separately warns that notes should not reuse the trapdoor. We did not find a wallet check in the crate. This site follows the deep dive here, since our example shows that the attack works, and out-of-band delivery does not change the arithmetic.

Why a spend publishes two nullifiers.

We can now return to the rule that the opening chapter stated and tested with labels. A spend with a target epoch proves that each epoch's nullifier is absent from the epoch with the same number, for every closed epoch from the note's creation up to the one before the target. Validators keep the tachygrams of the current and preceding epochs. Validators also accept a stamp for an epoch during that epoch or the next, because a transaction may still be waiting when a new epoch begins. Neither a miner nor a sync service can update the proof on the wallet's behalf.

A later proof looks for each nullifier only in the epoch with the same number. So the mechanism works only if a spend leaves a value where such a test will find it. The grace period threatens exactly this, because a spend with a given target may land in the next epoch.

Suppose instead that a spend published only its target's nullifier. A first spend with target seven waits in the mempool and gets accepted in epoch eight, so epoch seven's nullifier lands in epoch eight. A second spend with target eight now tests epoch seven's nullifier against epoch seven, where it is absent, and it publishes epoch eight's nullifier, which nobody has published. Both checks pass and the note is spent twice. Across all one hundred eleven scenarios we ran, forty-eight get through in this way.

Publishing the next epoch's nullifier as well closes this gap. A spend is accepted either in its target epoch or in the next one, and the pair covers both. So a spend accepted in some epoch always publishes that epoch's own nullifier during that epoch. That single fact carries the argument.

From this fact, the double-spend argument takes two cases. Take a first spend and a second spend of the same note, with the second accepted no earlier than the first. The first case is when the second spend's target comes after the epoch in which the first was accepted. That epoch is then closed and lies before the second target, so the second proof has to show that epoch's nullifier absent from that epoch. The first spend put it there, so the prover cannot build the proof.

The second case is when the second spend's target is no later than the epoch in which the first was accepted. The second spend's acceptance is at most one epoch past its target, and it is no earlier than the first spend's acceptance. So the first spend's acceptance epoch is either the second target or the epoch right after it. The second spend publishes the nullifiers of both those epochs, so it repeats the value the first spend left. The same reasoning shows that the two acceptance epochs differ by at most one, so the first spend's epoch is still retained, and validators reject the duplicate. This is also why the window needs two epochs.

To see the need for that second epoch, take two spends with target seven, the first accepted in epoch seven and the second in epoch eight. The colliding values entered the pool during epoch seven, so a validator that kept only the current epoch would miss them when the second spend arrives.

The argument assumes that a spender cannot choose nullifiers, which the commitment chain covered, and that nobody can forge proofs. The script checks this on every pair of spends of our note, with targets from epoch three to epoch nine and each spend accepted in its target epoch or the next. There are one hundred eleven such scenarios. In seventy-two of them the second proof cannot be built, and in the other thirty-nine consensus finds a shared value in its window. No scenario escapes. The two checks also overlap in six scenarios, where the first spend was accepted on time and the second targets and lands in the very next epoch, so the window would have caught it too.

This argument is reconstructed from the code at the commit this site pins, and the authors have not confirmed it. The rules come from the deep dive's consensus section, which argues by listing the safe cases for each acceptance time. The single fact about each epoch's own nullifier and the two-case argument are our restatement. The spend bind step derives the pair as described, and a comment on the tachygram type states the window rule, but we did not find the window scan itself in the crate. The tachygram page adds a second reason for scanning a whole epoch, which the next chapter explains.

Publishing the pair has a cost in the circuit, because the two values do not always come from one sponge. Our note's pair shows why. Epoch seven's nullifier comes from the group starting at four, while epoch eight's comes from the group starting at eight, so this pair needs two sponges. A spend with target five would find both of its values in the group starting at four. A circuit's shape cannot depend on secret values, as the arithmetization chapter explained, so the spend bind step runs two sponges in every case. The pair also needs a following epoch, so the code refuses a spend in the final epoch.

Tachygrams and output padding.

Earlier Zcash pools keep commitments in a Merkle tree and nullifiers in a separate set. Tachyon instead treats both as one kind of value, a tachygram, which is a thirty-two byte element of the coordinate field. A single structure can answer both questions a spend asks, namely whether a commitment is present and whether a nullifier is absent, and consensus does not need to know which kind a value is. This also helps privacy, as long as the published values give no other hint of their kinds.

Counting gives such a hint. A bundle already reveals its number of actions, because each action has one signature. A spend publishes two nullifiers and an output has only one commitment, so without further care the total would reveal the split. Take four actions. With no spends the total is four, with one spend it is five, and with four spends it is eight. An observer who subtracts the number of actions from the total gets the number of spends.

The deep dive notes that the leak is only about the count, since tachygrams never sit beside a particular action. To remove it, each action publishes exactly two. A spend publishes its pair, and an output publishes its commitment and a padding tachygram. So four actions now publish eight tachygrams, whatever the split.

The pad cannot be any easily computed function of the commitment. To see what an observer could do if it were, take one bundle with four actions, two of each kind. It publishes nine tachygrams, and the stamp lists them in sorted order. Suppose outputs derived the pad as a hash of the commitment. An observer holding the nine published values hashes each one and looks for the result in the list, which takes seventy-two ordered comparisons. With that design, the test finds exactly two matches in our bundle, and so the observer learns the output count. Run the same test on the bundle where each pad comes from the note opening, and it finds no matches. To test the real relation, the observer would need all four fields of the note.

So Tachyon derives the pad from the note opening, as a Poseidon hash of the same four inputs as the commitment, under a different domain. The hiding that the commitment gets from its trapdoor also hides any relation between the two values, and the domain tag is the only thing separating the pad from the commitment.

The sources differ on the pad's construction. The deep dive hashes an arbitrary preimage and calls the result a dummy. The tachygram page and the code, at the commit this site pins, have the pad commit to the note opening, and the output bind step computes both values from the note. Both forms resist the pairing test, so the disagreement is about construction, and this site follows the code.

The sources also differ on tachygrams per action. The bundle page says an action is bound to one tachygram, and the deep dive's accumulator section defines one per action, while its transaction section and the code use two. This site follows the code, with two per action and one more per bundle.

That extra one explains why our bundle has nine values rather than eight. Each bundle's fee change note publishes only its commitment, even when its value is zero, so a stamp holds two tachygrams per action plus one per bundle. The extra one appears once per bundle whatever the bundle does, so it adds nothing about the split. The aggregation chapter covers fees.

A stamp holds its tachygrams as a flat list, and the wire format requires them to be unique and sorted by their byte encoding. Sorting erases the order in which actions contributed them, and in the code a spend's step commits its pair as a set. Every published value must also be nonzero, which keeps each factor of the polynomial in the next section from degenerating. The book's proof tree page gives a different reason, a collision with the note's own commitment, and we did not establish that one independently.

These privacy statements cover what the published values reveal. As the chapter introducing proof-carrying data records, Ragu's book and code do not yet establish zero knowledge, so a separate question remains about what a proof itself reveals.

One structure for both tests.

We can now see why one kind of value is enough. A stamp's set of tachygrams corresponds to the polynomial whose roots are its members. A value is present exactly when the polynomial vanishes there, and absent when it does not, and neither test cares about the kind of value. In our bundle, the polynomial vanishes at the first output's commitment and at the first spend's nullifier for epoch seven, and the test has no need to know which kind each root is. Epoch nine's nullifier was not published, and the polynomial is nonzero there.

A spender uses the first kind of test to show that its commitment was published, and the second to show that an old nullifier was not. The next chapter develops these polynomials and their commitments.

Where these derivations run.

Each object in this chapter is computed inside a step of the proof tree, and the wallet runs all of these steps, which the chapter on the proof tree walks through in order. Note seed derives the payment key from the proof authorizing key, and then the master key and the commitment. Nullifier derive computes a window of nullifiers. Spend bind derives the published pair and checks that both values are nonzero. Spend action checks the proof authorizing key against the payment key, derives alpha and the randomized key, and commits the pair. Output bind derives the commitment and the pad from a note.

What comes next is reconstructed from the code at the commit this site pins, and the authors have not confirmed it. At this commit, Tachyon builds Ragu with its mock feature, and these steps compute hashes natively. Comments mark the known gaps. A real circuit needs a low-bit decomposition of each epoch to find the group start, since any field element can be written as four times something. It also needs a bit decomposition of alpha to use it as a scalar. So our statements about what a proof forces describe the design that the steps declare, and we did not find real circuits enforcing them in this crate. The gate counts we quoted come from the analysis page, and they are estimates for those circuits.

Where this chapter leaves us.

A wallet derives two children from its spending key, one to authorize spends and one to derive nullifiers. The payment key hashes the public signing point and the nullifier key, and wallets mint a fresh one per sender. A note holds a payment key, a value, and two trapdoors, and each action signs with a key randomized by alpha, so a published key is consistent with every possible owner.

A note's master key and a group start give four consecutive epoch nullifiers from one sponge, and cost in the proof is the reason this replaced the archived GGM tree. The commitment holds a spender to one nullifier sequence, assuming Poseidon resists collisions, and reused trapdoors remain a danger that the wallet must detect. A spend accepted in some epoch always publishes that epoch's nullifier, and this fact, the exclusion proof, and a two-epoch window together catch every double spend. Each action publishes two tachygrams and each bundle one more, so an observer learns the number of actions and not the split between spends and outputs.

All of this is a design at one commit of a proposal that has not activated, and these steps still run against a mock of Ragu. We have spoken of values being published in the pool without saying how a proof can refer to history that validators have forgotten.
