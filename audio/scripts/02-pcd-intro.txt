Chapter two. An Introduction to Proof-Carrying Data.

In the previous chapter, we saw why today's shielded pool is hard to scale. Every spend publishes a nullifier and every new note adds a commitment, so each validator keeps a nullifier set and a commitment tree that grow forever. Tachyon gives a note a different nullifier in each epoch, which lets validators keep only a short window of recent values. Wallets prove the rest themselves, by showing that their nullifiers never appeared in the older history that validators have forgotten. Those proofs have to extend and merge earlier proofs, so Tachyon needs proofs about proofs, and this chapter picks up from there.

Tachyon needs proofs from many separate wallets to collapse into one proof that a validator can check quickly, and anyone should be able to continue that combining later. This chapter states that requirement precisely, as a goal called proof-carrying data. It does not yet explain how to build it.

We treat the proof as a black box throughout, and the rest of the site opens that box. Most of the chapter works through a small sum on a tree, with no cryptography, so that each idea has concrete numbers. A short section then introduces Ragu's version of the model, and the chapter ends by mapping the same ideas onto Tachyon's aggregation.

The goal of proof-carrying data.

A proof system lets a prover convince a verifier that a computation was carried out correctly. The verifier receives a proof, and checking it costs much less than rerunning the computation. For this chapter we rely on two promises from the proof system. An honest prover can always produce a proof that the verifier accepts. And a prover cannot produce an accepted proof of a false claim, except with negligible probability. The chapter on statements and challenges makes these promises more precise.

Now consider a validator facing thousands of shielded transactions, each built by a different wallet from its own secrets. Using a proof system once for each transaction, or once for all of them together, runs into three obstacles.

The first obstacle is that one prover would have to hold everything. A single proof about a thousand transactions, produced in one run, would need one party holding the secrets of a thousand wallets. No such party exists, and no wallet would hand its secrets over.

The second obstacle is that finished proofs would not build on each other. If one more transaction arrives after the proof is done, the prover has to start again from the beginning.

The third obstacle is that separate proofs would keep the verifier's work high. With one proof per transaction, the validator performs one check per transaction, so the cost grows with the number of transactions.

Proof-carrying data avoids all three by changing what gets proved. We split the computation into steps arranged as a tree. Each node of the tree produces a piece of data together with a proof, and that proof covers the step at this node and every step below it. The data therefore carries evidence of its whole history, which is where the name comes from.

A proof-carrying data system should provide three properties, each answering one of those obstacles. The first is distributed work. The party running a node needs the data and proofs of the nodes directly below it, plus its own private input, and it does not need the private inputs of earlier nodes. The second is extension. Anyone holding a finished node can use it as an input to a new node, and nobody repeats the earlier proving work. The third is succinctness, which means the proof's size and the cost of checking it do not grow with the size of the tree.

Tachyon's aggregation is the application we have in mind, and the end of the chapter returns to it. In Tachyon, a wallet proves that its transaction follows the rules and publishes the result as a stamp. An aggregator combines stamps from independent wallets into a single stamp, and validators check that one stamp in place of the separate ones.

Tachyon has not activated on mainnet and its design is still changing, so everything this chapter says about it describes the Tachyon repository at the commit this site pins. That crate builds against a mock of Ragu. So when we say that a Tachyon step checks something or that a proof fails, we mean what the design expects. At this commit the step bodies run natively, with no real circuits, and we did not find a validator in the crate.

A toy computation.

To see what each node of a tree claims, we need a computation whose intermediate results are easy to check by hand. Adding up a list has this property, because a subtotal is meaningful on its own and two subtotals combine by addition. Our list has eight entries, which are four, eleven, three, seven, six, two, nine, and five. Their sum is forty-seven.

Treat the list as fixed. A party holding a given position can read the entry there, and other parties cannot. We want to reach one short statement about the total that a verifier can accept without ever seeing the list. Getting there requires deciding what each node claims and what rule a node must obey. The proof itself comes after that.

Headers.

We call the data at a node its header. A header has two jobs. It has to give the next node enough information to apply its rule, and it has to stay small, because it travels up the tree with the proof.

The first candidate for a header is the subtotal alone. A rule for combining two nodes would then add their subtotals and output the result. Here is how this candidate fails. Combining the entry with value eleven with itself produces a node that claims twenty-two, and nothing in that header reveals the repeat. A prover choosing any entry for each leaf can reach seventy-one different root totals from sixteen to eighty-eight. Only forty-seven is the true sum, yet every one of these trees passes a rule that checks only addition.

The trouble is that a bare subtotal does not say which entries went into it. No rule that reads only subtotals can reject a repeated entry, so the header has to record more. Adding the range of positions it covers fixes this. Our header becomes three numbers, a start position, an end position, and a sum. It claims that the entries from the start up to the end add up to that sum.

The range includes its start and excludes its end, so a range ending at some position meets the next range exactly when that next range starts at the same position. The header stays at three numbers however many entries it covers, because it records only the conclusion. It forgets the individual values and the order in which they were added. So choosing a header means deciding what to remember, and a good header keeps exactly the values that later rules need to compare.

Steps.

A header's claim means nothing without rules saying how a header may be produced. We call such a rule a step. A step declares the headers it takes as input and the header it produces, and it states a check that must pass. It may also use private input known only to the party running it, which we call the witness.

Our computation needs two steps. The first has no inputs, and it starts a new header from a single entry, so we call it Entry. Its witness is a position and a value. It checks that the list really holds that value at that position, and it outputs a header whose range covers that one position and whose sum is the value.

The second step takes two headers and combines them, so we call it Join. It checks that the end of the first range equals the start of the second. It outputs a header running from the first range's start to the second range's end, whose sum is the two sums added together. That check on the range boundaries is the part that the sum-only header could not express, because it rejects any pair of ranges that repeat, overlap, or skip entries.

Before attaching any proof, we can test whether these two steps are strong enough, by listing everything they can ever produce. Start from the eight entry headers and apply the join rule until nothing new appears. The process produces thirty-six headers, one for each range of positions, and each one states the correct sum for its range. Exactly one of them covers the whole list, and it says that positions zero up to eight sum to forty-seven.

This is the property we need from headers and steps together, because it means every header the rules can produce is true. The property has nothing to do with cryptography. It is a fact about the rules, and the application designer is responsible for it. The proof system's job comes later, and it is limited to making sure that nobody can present a header the rules could not have produced.

Running the tree.

We can now run the computation. Eight Entry steps produce one header per position. Then Join steps combine neighbors, giving twenty-five for the left half and twenty-two for the right half. At the last join the boundary check passes, since both sides name position four, and the sum comes to forty-seven. Each node depends only on the nodes it names as inputs, because their headers already summarize everything below them.

That tree is balanced, but the rule does not require it. A list of eight entries has four hundred twenty-nine binary tree shapes that keep the entries in order, and running all of them gives the same root header every time.

This freedom means the work can follow whoever holds the data. Suppose Alice holds positions zero to three and Bob holds the rest. Alice runs her subtree and hands over the header for her half, with sum twenty-five, along with its proof. Bob does the same for his half, with sum twenty-two. Carol, who holds neither half of the list, checks only that the boundaries meet and that twenty-five plus twenty-two is forty-seven, and then she produces the root header. Carol needed neither Alice's values nor Bob's, which is the distributed work property in miniature.

One particular shape deserves its own name. If each new node combines the previous result with one new entry, the tree becomes a chain. The chain form is incrementally verifiable computation, which Valiant introduced before the general tree form, and Chiesa and Tromer's proof-carrying data extended the idea to nodes with several inputs. A chain suits a single party working through a sequence, but it forces independent parties to wait for each other.

Tachyon needs both shapes. The exclusion proof from the previous chapter grows by one epoch at a time, which is a chain. Aggregation combines stamps from wallets that work independently, which needs a tree.

A finished node can also feed more than one later node, because a header and its proof are ordinary data that anyone can copy. For example, Alice's header, with sum twenty-five, can be joined with Bob's header to give forty-seven. The same header, with the same proof, can also be joined with a header covering positions four up to seven, with sum seventeen, to give forty-two. Nobody has to rebuild Alice's header for the second use.

So the history of a proof can share nodes, and the literature describes it as a directed acyclic graph. Tree remains the common name, and it is accurate for the way we draw the inputs of any one node.

Attaching a proof.

So far a verifier would have to trust whoever ran the nodes, or else rerun all of them. We now attach a proof to each node, so that a node's output is the pair of a header and a proof. The proof at a node establishes the following statement. There is a witness for which the declared step accepts these input headers and produces this output header, and each input header has a valid proof.

The last clause makes the statement recursive, which is the central idea of proof-carrying data. A node proves that its children's proofs verify, so a later verifier does not have to see those children. How a proof can contain a check of another proof is the subject of the chapter on recursive proofs, and the section on succinctness says what this asks of the proof system.

Unwinding the statement at our root shows how much a single proof covers. The root header says that the Join rule accepted the two half headers, and that those headers have valid proofs. Following every branch to the bottom reaches eight Entry checks, each comparing one value with the list. So the root's proof stands for all fifteen checks in the tree, of which the verifier runs none.

The verifier's procedure has two parts. It runs the proof system's check on the header and proof, and then it compares the header with the question it actually wants answered. The second part matters even when every proof is valid. A header covering positions zero up to seven, with sum forty-two, is also true and has a valid proof. A verifier who accepted it without confirming the range would conclude that the total is forty-two.

Why a false header has no proof.

The argument rests on three assumptions. First, the proof system keeps its promise, so accepted proofs of false statements do not occur in practice. Second, the steps are correct, so a step with true input headers can only output a true header. Third, the verifier compares the final header with what it wants to know.

Suppose a prover holds an accepted proof for a false header. By the first assumption, the node's statement is true, so a declared step accepted some input headers and produced this one, and those inputs have valid proofs. By the second assumption, the inputs cannot all be true, or the output would be true as well. So at least one input is a false header with a valid proof, and the same reasoning applies to it. Each repetition moves one level down the tree. The descent eventually reaches a step with no inputs, such as Entry, whose check rejects a false entry directly. So a prover cannot obtain a valid proof of a false header.

This descent is informal in one respect. Soundness makes accepted proofs of false statements infeasible to find, but such proofs can still exist, so the claim that those inputs have valid proofs does not by itself show that anyone holds them. The argument really needs a prover who produces a proof to know the child proofs as well. That is the knowledge soundness of the next chapter, and the chapter on recursive proofs returns to this point.

Here is what each natural attempt to cheat runs into on the toy tree. A prover who claims that position two holds four fails at the Entry check, because that position holds three. A prover who joins four and eleven and claims sixteen fails at the addition in Join. Repeated entries, overlapping ranges, and skipped entries all fail the boundary check. In each case the prover cannot obtain a proof for the node where the falsehood first appears, so no later node can use it as an input.

Succinctness.

The node's statement could be met in a wasteful way, by having each node attach its children's proofs to its own. The pile of proofs would grow with the tree, and the verifier would check each one. With one thousand twenty-four entries that means two thousand forty-seven proofs. With proof-carrying data, the verifier checks one proof in every case.

A tree also saves time. A balanced tree over one thousand twenty-four entries has eleven layers. With enough workers, all the nodes of one layer can run at the same time, so the number of rounds grows with the logarithm of the number of entries.

Succinctness is not only a convenience for the final verifier. Each node has to check its children's proofs as part of its own statement. If checking a proof grew with the size of the history behind it, every level of the tree would cost more to prove than the one below, and the recursion would soon become impractical. So a proof system usable for proof-carrying data needs a check that stays small no matter how much history the proof covers. Most of the machinery on this site exists to meet this requirement, and much of the difficulty lies in making that check cheap enough to run inside another proof.

Headers face the same limit. That is why, near the end of the chapter, we will find commitments where a stamp's growing sets might have been.

Proof-carrying data in Ragu.

So far we have described proof-carrying data in general. Ragu, the proof system this site studies, implements this model, and two of its choices matter before the rest of the site opens the box.

The first is its vocabulary. In Ragu, a header type defines the form of a node's data, and a step declares a left input header, a right input header, an output header, and a witness. Ragu calls the operation that runs a step on two input nodes and produces a new header with its proof fuse.

The Ragu Book chose the word fuse to avoid the word folding, which names a different operation in later chapters. The Tachyon book says merge for what its aggregators do. This site says fuse for Ragu's operation, and it keeps merge for particular Tachyon steps, such as Stamp Merge, and for what those steps do to stamps.

Every Ragu step has exactly two inputs. A step that needs fewer, such as Entry, fills the unused ones with the unit header, which carries no data. The chapter on recursive proofs explains this choice and how the first nodes of a tree get started.

Proof size and hiding.

The second choice concerns size. Ragu meets the size requirement in two forms. The proof a node holds while fusing has a fixed size however large the tree behind it, but it is large, because it still contains data that a parent needs for its own work. Later chapters describe that data.

When a proof leaves the tree for a party that only wants to check it, Ragu's compress operation turns it into a proof that a code comment puts at a few kilobytes. At the commit we read, a compressed proof cannot be fused any further. The sources disagree about how an aggregator will fuse proofs that arrive compressed, and the chapters on recursion in Ragu and on aggregation set out each position.

Everything in this chapter concerns correctness, and nothing so far has required a proof to hide its inputs. The Tachyon book describes the stamp as a recursive zero-knowledge proof. The Ragu Book states that the current construction does not yet establish zero knowledge, and the code at the commit this site pins agrees.

This site follows the Ragu code and treats hiding as a goal that has not yet been met, which the chapter on recursion in Ragu examines. When we say that a node does not need its children's witnesses, we mean only that it can do its work without them.

Aggregation as proof-carrying data.

We can now map the toy onto Tachyon's aggregation. Each wallet builds a stamp for its own transaction. From an aggregator's point of view that stamp is a leaf, although the wallet's own steps form a tree beneath it. Only the wallet can build that stamp, because only the wallet holds the secrets those steps need. An aggregator then combines stamps without any secrets, because a merge reads only its children's headers and proofs.

Our example has three transactions, which we'll call X, Y, and Z. In the book's model, an aggregator always merges onto a bundle of its own, so we let the aggregator be the party that built X. It merges the stamps of Y and Z, which other wallets have sent to the mempool, onto its own stamp.

The stamp header.

The previous chapter divided a transaction's Tachyon bundle into a body and a stamp. The body holds, for each action, a value commitment and a randomized signing key, which together form the action's descriptor. It also holds the maximum fee commitment and the fee, which form the bundle's fee descriptor, together with the signatures. The stamp holds the tachygrams, the anchor, and the proof.

Hashing an action's descriptor gives its action digest, and hashing the fee descriptor gives the bundle's fee digest. A wallet signs a maximum fee once and picks the actual fee later, when the transaction goes out, so the signatures do not fix the fee. Putting the fee digest among the digests lets the proof fix it instead.

The header of a stamp's proof has three fields. The first is a commitment to the action set, which holds the stamp's action digests and fee digests. The second is a commitment to the tachygram set, where a tachygram is a published value that records the creation or destruction of a note. The third is an anchor, which names a state of the Tachyon pool that the stamp's spends refer to.

The sets grow as stamps combine, but succinctness requires the header to stay small, so the header holds commitments in place of the sets. A commitment is a short value that stands for a long list and cannot later be opened to a different one. The chapter on aggregation and bundles gives the exact hashes and commitments.

In our example, all three wallets built their stamps against the same anchor. X has one action, so its stamp covers two digests and three tachygrams. Y has two actions, three digests, and five tachygrams. Z has one action, two digests, and three tachygrams. Each action publishes two tachygrams, and each bundle adds one more for its fee change note.

Merging stamps.

The Tachyon step that combines two stamps is called Stamp Merge, and each part of it has a counterpart in the toy. A stamp's header, with its two committed sets and its anchor, plays the part of the three-number header. A wallet's finished stamp plays the part of a leaf from Entry.

The check that the two anchors are equal takes the place of the boundary check, because a merged stamp has a single anchor field and has to make all of its claims about one state of the pool. Unlike the boundary check, it does not stop an input from being counted twice, and we come back to that shortly. Stamps built against different anchors must first be moved to a common one, which the chapter on pool state explains.

In place of adding two sums, the merge combines two sets. Tachyon encodes each set as a polynomial whose roots are its members, and the step checks that each output polynomial equals the product of the two input polynomials. A product has the roots of both factors, so it encodes a multiset union, in which a member held by both inputs would appear twice. Honest inputs share no members, and for them this is the ordinary union.

The aggregator merges X with Y, and then merges the result with Z. The first merge passes the anchor check and gives a stamp covering five digests and eight tachygrams. The second gives seven digests and eleven tachygrams. The merged stamp stays on the bundle that supplied the left input, so the aggregator puts its own bundle X on the left. Its header is still two commitments and an anchor, the same size as before.

The next point is reconstructed from the code at the commit this site pins, and the authors have not confirmed it. Our toy Join rejected a repeated entry through its range check. In Stamp Merge we found only the product check, and no constraint that the inputs are disjoint. The Tachyon book lists the merged sets as exclusive, and the protection against repeats appears to come from the validator's checks on the published tachygrams. The chapter on aggregation and bundles works through those checks.

The block.

A merged stamp replaces the proofs of the transactions it covers, but the transactions themselves still go into the block, each with its own body. The Tachyon book names three states that a bundle can be in. An autonome comes from a wallet and carries a stamp whose proof covers only that bundle. An aggregate comes from an aggregator and carries a merged stamp that covers it and others. An adjunct has had its stamp stripped by a miner, and it points to the aggregate that covers it instead.

An aggregator sends its aggregate to the mempool as an ordinary transaction. A miner who includes it in a block also includes Y and Z, strips their stamps, and points them at X. Their signatures do not cover their stamps, so stripping leaves those signatures valid. Y and Z start as autonomes and end as adjuncts, which exist only on chain.

The block carries one proof where the three separate transactions carried three. It still carries all eleven tachygrams, inside the stamp on X, and every action and fee descriptor, inside the bodies.

To check the one proof, a validator needs its header. The stamp on X carries its tachygrams and its anchor, but no commitment to its action set. So the validator rebuilds that set. It hashes the descriptors in the bodies of X and of every adjunct that points to X, and it checks the proof against the header those values produce.

In our block the rebuilt set has seven members, which matches the merged stamp, so the proof verifies. If a miner leaves Z out of the block, the rebuilt set has five members instead of seven. If a miner instead adds a one-action bundle that the stamp never covered and points it at X, the rebuilt set has nine members. In both cases the rebuilt header differs from the one the proof was made for, so the proof fails.

This rebuild is the verifier's comparison at work. In the toy, a verifier who wanted the whole sum had to confirm that the range ran from zero to eight. Here the validator confirms that the proof covers exactly the bundles in the block. This is why a miner who includes an aggregate must include every bundle it covers.

The validator also checks the anchor against the chain. The step that starts a stamp takes its anchor as a free witness, meaning a witness value that no check constrains, so the proof alone cannot show that the anchor is real. That check is the third assumption of the soundness argument, in Tachyon's setting.

The chapter on aggregation and bundles covers what this section leaves out. That includes fees, aggregates whose own bundle has no actions, what an aggregator does when some of its inputs are mined first, and the wire format.

The rest of the proof tree.

Stamps sit at the top of a larger tree, and different parties run its nodes, which is the distributed work property at full scale. A wallet's own steps build its stamp from its notes and keys. An untrusted sync service supplies evidence that the note being spent was not spent in earlier epochs, and it does this without seeing the note or its commitment.

In outline, one spend reaches an aggregate like this. The sync service's evidence feeds the wallet's steps for the note, its nullifiers, and the spend. Those steps produce a header covering the bundle's actions. A last wallet step called Fee Fuse turns that header into a stamp by applying the fee chosen after signing. The stamp then enters Stamp Merge at the aggregator, alongside other wallets' stamps.

The chapter on the proof tree walks through every step in this picture. Before that, the chapters on notes and nullifiers, on pool state, and on oblivious sync build the objects those steps handle.

Where this leaves us.

Let's collect what we've built. Proof-carrying data arranges a computation as a tree of nodes, where each node produces a header and a proof covering everything below it. A header has to hold enough for later rules to catch repeats and gaps while staying a fixed size. A step is the rule relating input headers and a witness to an output header, and correct steps can only produce true headers.

A node's proof states that its step accepted its inputs and that those inputs have valid proofs. This recursion lets one proof stand for the whole tree, provided the verifier also compares the final header with what it wants to know. Each node has to run the proof check on its children, so that check has to stay small.

Ragu runs each step through an operation called fuse, with two inputs at every node. Its proofs keep a fixed size while fusing and shrink when compressed, and they do not yet hide their inputs. Tachyon's aggregation applies this model to stamps. A validator rebuilds the merged stamp's header from the block, so aggregation removes proofs from the chain while keeping every descriptor and tachygram.

Everything here assumed a proof system that can prove a step's check and verify another proof inside a step. The rest of the site builds that system. The next chapter, Statements and Challenges, starts with what it means to prove a statement and how random challenges make a large check small.
