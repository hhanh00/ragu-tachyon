Chapter eight. Batched openings.

The inner product argument proves one evaluation claim about one committed polynomial. A complete proof makes several such claims, about different polynomials at different points, and running the argument once per claim multiplies its cost. In this chapter we reduce any number of claims to a single claim, so that the argument runs only once.

The reduction has two stages. The first moves every claim to one fresh random point with the help of quotient polynomials. The second combines the resulting claims at that point using a random linear combination. The Ragu Book calls these stages alpha batching and beta batching after their challenges, and the literature calls the whole technique a batched opening or a multi-opening.

Several sections compare this description with Ragu's code. Every statement in this chapter about what the code does is reconstructed from the code at the commit this site pins, and the authors have not confirmed it.

Why a proof makes many claims.

The next chapter assembles a complete proof, and the final step of that proof in the Ragu Book lists the claims that the verifier needs checked. We'll meet those polynomials properly in that chapter, so for now only the shape of the list matters. It has two claims about one polynomial, one claim each about two others, and two claims about a fourth. In the book, one of those claims says a polynomial takes the value one at zero, and the next chapter explains why the code's value differs, though the difference doesn't change the shape of the list. One of the polynomials has two variables, but once a challenge fixes the second variable, it behaves as an ordinary polynomial, so its claim has the same form as the others.

That makes six claims about four polynomials at four points. Later chapters add more, because a recursive step also has to handle the claims it inherits from earlier proofs. Opening each claim separately repeats the whole argument, with its group elements and its verifier work, once per claim. Near the end of the chapter we'll count what batching saves on this list, once we know what the batched argument sends.

We describe one claim by three things, namely a commitment, a point, and a value. The claim says that the polynomial behind the commitment takes that value at that point. Both parties hold these triples, and only the prover holds the polynomials. The goal is a short exchange after which both parties hold a single triple, with the property that a false input claim leads to a false output claim, except with negligible probability.

Combining claims at different points.

The random linear combinations from the chapter on statements and challenges already solve the problem when all the claims use one point. Suppose two polynomials have claims at the same point. The verifier picks a random number and asks about the first polynomial plus that number times the second. It can work out the combined commitment and the expected combined value alone, because commitments and evaluations combine with the same coefficients.

This method stops working when the points differ, because a combination of polynomials has no single point at which the combined claim makes sense. Here is an example, worked modulo forty-three as usual. The prover claims that one polynomial has the value thirty-seven at the point nine, and that a second polynomial has the value twenty at the point five. Both claims are true.

Take the multiplier six. The combination has the value thirty-six at nine and the value thirty-five at five, while the combined claim comes to twenty-eight. The claimed number matches neither value. The value at nine would need the second polynomial's value at nine, which is seven, and nobody has said anything about that.

So we need a way to convert a claim at its own point into a claim at a point shared by all the others. The verifier's challenge can supply such a point. What's missing is a way to restate the claim as a fact that holds everywhere, so that we can test it anywhere.

Writing a claim as a division.

A claim says that a polynomial takes a certain value at a certain point. Equivalently, the polynomial minus that value has a root at that point. Each root gives a linear factor, so the claim holds exactly when the polynomial minus the value equals X minus the point, times some other polynomial. We call that other polynomial the quotient of the claim.

To see how the prover computes the quotient, and why a false claim has none, take a polynomial with four coefficients. Its quotient has degree two, so it has three coefficients of its own. Multiply out the factored form and match each power of X on the two sides, which gives four equations.

The first three equations fix the quotient from the top down. The top coefficient of the quotient equals the top coefficient of the polynomial. Each lower coefficient equals the next coefficient of the polynomial, plus the point times the quotient coefficient you just found. The claimed value plays no part in those three equations.

Only the last equation mentions the claimed value, and rearranging it says that the claimed value must equal the polynomial evaluated at the point. So the system has a solution exactly when the claim is true. This procedure is called synthetic division, and the same pattern works for any number of coefficients.

Here it is with numbers. Take the polynomial with coefficients seven, two, five, three, starting from the constant term, and the point nine. The top quotient coefficient is three. The next is five plus nine times three, which reduces to thirty-two. The next is two plus nine times thirty-two, which is again thirty-two. One more line of the same kind gives seven plus nine times thirty-two, which is thirty-seven. That last line recovers the value of the polynomial at nine, and the quotient has coefficients thirty-two, thirty-two, three.

Now suppose the prover claims thirty-eight at nine instead. The first three lines don't involve the claimed value, so they produce the same quotient. The last line still computes thirty-seven, which contradicts the claim. No polynomial can repair this. At the point nine, X minus nine is zero, so the factored form is zero whatever the quotient is, while the polynomial minus thirty-eight equals forty-two there. Written with that leftover constant, the division says the polynomial minus thirty-eight equals X minus nine times the quotient, plus forty-two.

The same thing happens in general. The first three lines give the same quotient whatever the claimed value is, and the last line leaves over a constant, the true value minus the claimed value. We call that constant the error of the claim, or the remainder of the division. It is zero exactly when the claim is true, and a claim has a quotient polynomial exactly when its error is zero.

For a false claim, the fraction of the polynomial minus the value, over X minus the point, still exists as a rational function, which means a fraction of two polynomials. It equals the quotient plus the error over X minus the point. That second term cannot be simplified to a polynomial, and it has no value at the claimed point, where the denominator is zero. We call such a point a pole. No polynomial has a pole, so no polynomial can agree with this fraction everywhere, and the protocol relies on that difference.

Moving one claim to a new point.

The factored equation is an identity between polynomials, so it holds at every point. At any new point other than the original one, we can divide by the nonzero difference between the two points. This says that the quotient's value at the new point equals the polynomial's value there minus the claimed value, divided by the difference of the points.

That relation gives us a test at a point unrelated to the original. The prover commits to the quotient first, which fixes it. The verifier then picks a random new point, and the prover sends the polynomial's value there. The verifier computes what the quotient's value has to be from the relation.

What remains are two claims at the new point. The original commitment must open to the sent value, and the quotient's commitment must open to the computed value. The original point now appears only in the verifier's arithmetic, and in no remaining opening.

Take a small example, using the second polynomial from before. Its coefficients are three, one, eight, four, and its claim is the value twenty at the point five. Division gives a quotient with coefficients twelve, twenty-eight, four. The prover commits to the quotient, and the verifier sends the new point seventeen. The prover sends eleven, the polynomial's value at seventeen. The verifier computes eleven minus twenty, divided by seventeen minus five, which is ten modulo forty-three. Evaluating the quotient directly at seventeen confirms the ten.

For one claim this looks like a step backward, because it replaced one opening with two. The gain appears with several claims, since every claim can use the same new point. Three claims at three different points become openings that all sit at the new point, and then the same-point method from earlier merges them into one.

The test also behaves well against a false claim. For now, assume the prover sends the true value at the new point, which the opening of the original commitment enforces, and we'll deal with a prover that lies later. Whatever polynomial the prover commits to differs from the rational function, so the relation gives the wrong value at most new points.

To count the exceptions, multiply through by the difference of the points. The relation then holds only where two polynomials agree. One is the committed polynomial times X minus the point, and the other is the original polynomial with the claimed value subtracted. They differ because a false claim has no quotient. The commitment limits the degree of their difference to at most the number of coefficients, so the difference has at most that many roots. The prover's chance of passing is therefore at most the number of coefficients divided by the size of the field.

Alpha batching.

With many claims, a separate commitment to each quotient would add one curve point per claim to the proof. Commitments add the way polynomials do, so the prover can send one commitment to a combination of the quotients instead. Our running example has three polynomials with one claim each. The first has the value thirty-seven at nine, the second has the value twenty at five, and the third has the value forty-one at two.

A small oddity of the toy curve shows up here. The third polynomial's commitment is the same point as the quotient commitment from the last example, although the two polynomials differ. The toy group has only forty-three elements, so unrelated lists often share a commitment. On a real curve such a collision would break binding.

A plain sum of the quotients would be safe if every claim used its own point, because an error over X minus five and an error over X minus nine cannot cancel each other. The running example has distinct points, but real lists don't. The list at the start of this chapter has two claims at the point zero, about two different polynomials. Errors at a shared point can cancel, because two false claims at the same point have their errors over the same denominator, and a cheater can choose those errors to be opposite.

For this one example, move the first two claims both to the point nine. The true values there are thirty-seven and seven. A cheater claims thirty-eight and six, so both claims are false, but the errors are opposite. The sum of the two polynomials minus the sum of the two claimed values still has a root at nine, and division leaves no remainder. The result is a genuine polynomial, which the cheater can commit to and open at any point.

Giving each quotient a different random weight prevents this, for the same reason that powers of one challenge worked in the chapter on statements and challenges. After the claims are fixed, the verifier sends a challenge called alpha, and the prover forms a weighted sum of the quotients using powers of alpha. With three claims, the first quotient gets alpha squared, the second gets alpha, and the third gets a weight of one. We'll call this combination f. The first claim takes the highest power because that is the order Ragu's code uses, and we'll compare it with the book's order shortly.

To see what the weights do to false claims, compare f with the combined fraction, the same weighted sum taken over the claims' fractions instead of their quotients. Each fraction splits into its quotient plus its error over X minus its point. The quotient parts add up to f. The error parts that share a point share a denominator, so they add into one term per point.

We call the weighted sum of the errors at one point the combined error at that point. When every claim is true, every combined error is zero and the combined fraction equals f. The combined fraction has a pole at a point exactly when the combined error there is nonzero. With one claim per point, the combined error is a single weighted error, which is nonzero whenever that claim is false. That's why a plain sum is safe in that case.

With several claims at one point, the weights make it unlikely that their errors cancel, and the plain-sum attack shows by how much. With the weights alpha and one, the two opposite errors leave a combined error of alpha times forty-two, plus one, over X minus nine. Trying all forty-three values of alpha shows that only alpha equal to one removes it, and that value is the plain sum.

The prover now computes f for the running example. Take alpha equal to eleven, so that alpha squared is thirty-five. Combining the quotients gives a polynomial with coefficients three, twenty-five, twenty-six. Each quotient has one coefficient fewer than the polynomials, so the prover pads f with a zero in the top position to fit the generators. It commits to the padded list and sends one curve point.

That commitment fixes f before the next challenge. The prover has not sent any of the individual quotients, and the verifier doesn't need them.

Moving every claim to one point.

The verifier now sends a random point, which we'll call the shared point. Earlier we found a relation that gives one quotient's value at a new point. The polynomial f is a weighted sum of the quotients, so the same weights carry over to its value. For each claim, subtract the claimed value from the polynomial's value at the shared point, divide by the difference of the two points, and multiply by the claim's weight. The value of f is the sum of those results.

The verifier already holds everything in that formula except the polynomials' values at the shared point. So the prover sends those values, and the verifier computes the value of f for itself. The formula divides by the difference between the shared point and each original point, which fails if the shared point lands on an original point. In a field of about two to the two hundred fifty-four elements, the chance of that is at most the number of claims divided by the size of the field.

One place where Ragu runs this protocol is compression, the operation from chapter two that turns a fused proof into a short final proof. The compression verifier rejects if the shared point lands on a claim point. The toy field has only forty-three elements, so the worked examples draw the shared point only from values that avoid the claim points.

Take the shared point seventeen. The prover sends fourteen, eleven, and one, the three polynomials' values there. The verifier works out one weighted term per claim, which come to twenty-three, twenty-four, and twenty-six, and their sum is thirty modulo forty-three. The prover, who holds f, gets the same thirty by direct substitution, so the verifier has obtained this value without seeing f.

Let's take stock of where the argument has got to. The verifier now holds one claim per polynomial plus one more for f, and all of them use the shared point. The obstacle from earlier has gone, because no remaining opening refers to the original points. The original claims have not disappeared, though. Each original point and claimed value now sits inside the formula for the value of f, and a false claimed value makes that number wrong.

Beta batching.

Since all the claims now use one point, a random linear combination finishes the job. After the prover has sent its values, the verifier sends a challenge called beta, and the prover forms one combined polynomial. With three claims, f gets beta cubed, the first polynomial gets beta squared, the second gets beta, and the third gets a weight of one.

The verifier cannot compute this polynomial, but linearity gives it everything else. The homomorphic property gives the combined commitment, using the same weights on the commitments. The combined value comes from applying the same weights to the values at the shared point. The output is a triple made of the combined commitment, the shared point, and the combined value, which is exactly the kind of claim the inner product argument proves.

One naming warning helps here. The commitments chapter used the letter P for a statement point, which combined a commitment with a claimed value. The Ragu Book uses P for a plain commitment to the combined polynomial, so the statement point for the output claim is that commitment plus the output value times U.

Take beta equal to twenty-three, so that beta squared is thirteen and beta cubed is forty-one. Using only group operations and field arithmetic, the verifier gets the combined commitment and the combined value thirty-two. The prover combines the coefficients and gets twenty-seven, eight, twenty-nine, eight. Committing to those gives the same point, and evaluating them at seventeen gives the same thirty-two.

Every input to the combined polynomial, including f, needs a weight of its own. As we'll see when we look at cheating, errors in two inputs with the same weight can cancel for every beta. The book's formulas leave the weights partly open.

Here the Ragu Book and the code differ. The book writes f as a sum of powers of alpha times the quotients, and the combined polynomial as f plus a sum of powers of beta times the polynomials, without stating where the index starts. The compression verifier, at the commit this site pins, gives the first claim the highest power of alpha, gives f the highest power of beta, and gives the last polynomial a weight of one. This is reconstructed from the code, and the authors have not confirmed it. This site follows the code.

Read with the powers of beta starting at one, the book's formula gives distinct weights in a different order. That is equally safe, and it is the form the Halo two book uses. Read from a power of zero, it gives f and the first polynomial the same weight of one, and that shared weight is unsafe, as we'll show.

The complete protocol.

Now we can put the two stages together and follow what happens to the claims. Three claims at three different points become four claims at the shared point, including one about f, and then they become one claim about the combined polynomial.

The messages run in this order. Both parties start with the claims, and the verifier sends alpha. The prover computes the quotients and their combination f, and sends its commitment. The verifier sends the shared point, and the prover sends its values there. The verifier sends beta. The prover computes the combined polynomial, and the verifier computes the value of f, the combined commitment, and the combined value. Both parties then hold the single output claim.

The soundness of the protocol depends on this order, as we'll see shortly. Under Fiat-Shamir, each challenge becomes a hash of a transcript that has absorbed everything before it, including the claims themselves. The worked examples here use chosen challenges so that the numbers stay readable.

To finish our toy run, the prover reveals the combined polynomial, and the verifier checks directly that its coefficients commit to the combined commitment and that it evaluates to thirty-two at seventeen. Both checks pass. These final steps are the expensive ones. The NARK in the Ragu Book really does finish this way, with the prover sending the combined polynomial in full, and the next chapter returns to that choice. A succinct proof replaces the reveal and its checks with one inner product argument for the output claim, as compression does in the code.

Why cheating fails.

The argument relies on three assumptions. Commitments are binding under the discrete log relation assumption. The final opening is sound. And Fiat-Shamir challenges behave like uniform random values that nobody can predict before the preceding messages are fixed, which is the random oracle assumption.

Take one false claim in the running example, namely twenty-one for the second polynomial at five, where the true value is twenty. We first look at what the false value does to a run in which the prover otherwise follows the protocol. Then we go through the challenges in the order the protocol sends them, alpha, then the shared point, then beta, and ask at each stage what a cheater can try. On the toy field we count the cheater's success by trying every challenge.

The cheater reports true values.

A cheater who runs the honest division gets a perfectly good polynomial f, because division ignores the claimed value. It commits to the same f as before and reports true values at the shared point. The false value only shows up inside the verifier's formula. At seventeen, the verifier derives four, while f's value there is thirty. We measure the gap as the derived value minus the value of f, which is seventeen modulo forty-three.

That gap equals the combined error at five, divided by seventeen minus five. At alpha equal to eleven, the combined error is eleven times minus one, which is thirty-two, and thirty-two divided by twelve is seventeen modulo forty-three. We tried every pair of challenges. The shared point has to avoid the three claim points, which leaves forty allowed values, and beta can take all forty-three. The gap is nonzero at all forty shared points, and the only passing runs are the forty that have beta equal to zero.

The gap is never zero here, because the honest f is the polynomial part of the combined fraction, and the error term at five is the part left over. That combined error is the claim's weight times its nonzero error, and the weight is nonzero for this alpha, so the gap cannot vanish at any allowed shared point. The check passes at beta equal to zero only because that value removes f from the combined polynomial altogether. We'll return to that case at the stage for beta.

The cheater hopes for a cancelling alpha.

The gap depends on the false claim having a nonzero weight, and alpha sets the weights. We saw earlier that false claims at a shared original point can cancel for one particular alpha. A single false claim can also lose its weight entirely. In either case the combined fraction has no pole, so the cheater holds a genuine polynomial f that passes everything afterward.

In the running example only the second case can occur. The false claim's weight is alpha, so its combined error is forty-two times alpha, whose only root is alpha equal to zero. At that value the weights are zero, zero, and one, so the false claim drops out of f and the honest quotients pass. With alpha equal to zero, we checked all forty allowed shared points and all forty-three values of beta, and the cheater passes in all one thousand seven hundred twenty runs.

The same reasoning works with more claims. The combined error at a point is a polynomial in alpha, of degree at most the number of claims minus one, and its coefficients are the errors of the claims at that point. So it is nonzero whenever one of those claims is false, and a random alpha removes the pole with probability at most the number of claims minus one, divided by the size of the field. From here on we take alpha equal to eleven, which leaves the pole in place.

The cheater commits to something else.

With the pole in place, the honest quotients fail at every shared point, as the first example showed. The cheater's next option is to commit to some other polynomial before it sees the shared point, chosen so that the formula holds with true values at as many shared points as possible. That polynomial has degree at most the number of coefficients minus one.

To count the points where this can work, we turn the requirement into a polynomial equation. Suppose the claims use a certain number of distinct points, and multiply both sides by the product of the shared point minus each of them. That product cancels every denominator. Moving everything to one side leaves a polynomial in the shared point, with degree at most the number of coefficients minus one, plus the number of distinct points.

That polynomial is not identically zero. If it were, the committed polynomial would equal the combined fraction, and a polynomial cannot equal a fraction with a pole. So the cheater matches at most that many shared points.

In our example only one claim is false, which leaves a single pole at five. The requirement becomes the committed polynomial minus the honest f, times the shared point minus five, equals the combined error. The left side has degree at most the number of coefficients, which is four. It is zero at five while the combined error is not, so the equation cannot hold everywhere, and the cheater matches at most four shared points.

The cheater can reach that limit by interpolation. It builds a polynomial that matches the verifier's formula at the shared points three, eleven, seventeen, and thirty. If the challenge lands on one of those four, the cheater reports true values and passes for every beta. If it lands anywhere else among the forty allowed points, this polynomial doesn't match.

We tried all three million four hundred eighteen thousand eight hundred one polynomials of degree at most three. None matches the formula at more than four points. Exactly ninety-one thousand three hundred ninety reach four, one for each choice of four points.

The cheater lies about a value.

Once the shared point arrives, the cheater has committed and can no longer change f. To close the gap it can change a value that it sends at the shared point. This moves the error out of the formula for f and into the term for that polynomial, where beta catches it instead.

At seventeen the cheater sends twelve for the second polynomial, in place of the true eleven. It chooses that shift of one so that the derived value equals f's value of thirty. In effect it reports values of the second polynomial plus one, a polynomial that does satisfy the false claim, while its commitment still holds the original. The output claim now carries that shift. With beta equal to twenty-three, the combined value and the true value differ by twenty-three, so the check fails. Of the forty-three values of beta, only zero passes.

The cheater can also spread its lies across all the values. The difference between the combined value and the truth is then a polynomial in beta, whose coefficients are the error in the derived value of f and the errors in the sent values. All of its coefficients are fixed before beta is chosen, and its degree is at most the number of claims. If any coefficient is nonzero, at most that many values of beta make it vanish. They can all be zero only if true values satisfy the formula at the shared point, and that is the case the previous stage already counted.

On the toy field, with f and the shared point seventeen fixed, the cheater can send any of seventy-nine thousand five hundred seven triples of values. We tried all of them against every beta, and no triple passes for more than three values of beta. That agrees with the error being a nonzero polynomial of degree at most three in beta.

Two inputs with the same weight.

The stage for beta relied on each input having its own power of beta. Then each error sits in its own coefficient, and a lie in one value cannot offset a lie in another for every beta. If two inputs share a weight, their errors land in the same coefficient and can cancel there. The book's formula read from a power of zero gives f and the first polynomial the same weight, and the next example exploits that.

Take the same false claim, but start both sums at zero, so that f and the first polynomial both have a weight of one. The cheater commits to the honest f under these weights. At the shared point seventeen, with true values, the derived value falls twenty-six short of f's value. The cheater then sends eighteen in place of the true fourteen for the first polynomial, a shift of four. That shift changes the derived value of f and also the first polynomial's term in the combined value, and the two changes add up to exactly the miss.

No power of beta appears in this equation, so the forged message passes for all forty-three values of beta. The attack works at thirty-nine of the forty allowed shared points, which is one thousand six hundred seventy-seven of the one thousand seven hundred twenty pairs of challenges.

We don't suggest the authors intend this reading of the book, and the code's distinct weights have no such collision. The collision comes from the beta sum alone, so the range of the alpha sum makes no difference to it.

Adding up the stages.

A cheater wins a run if alpha removes the pole, or else if the shared point lands where its committed polynomial matches, or else if beta lands on a root of its error polynomial. To bound its chance over all three challenges on the toy field, we need the counts for every alpha, while the searches so far used only alpha equal to eleven.

The equation from the stage for the shared point covers every nonzero alpha. The combined error is alpha times the claim's error. Divide both sides of the requirement by the shared point minus five and by alpha. The right side becomes the claim's error over the shared point minus five, which doesn't mention alpha. As the committed polynomial ranges over every polynomial of the allowed degree, so does its difference from f divided by alpha. So the set of shared points a cheater can match is the same for every nonzero alpha.

Now add up. At alpha equal to zero, the cheater wins all one thousand seven hundred twenty pairs of the other two challenges. At each of the other forty-two values of alpha, it wins on at most four shared points outright, and on at most three values of beta at each of the other thirty-six. That comes to at most two hundred eighty pairs. In total the cheater wins at most thirteen thousand four hundred eighty of the seventy-three thousand nine hundred sixty triples of challenges. Stage by stage, the bad values are one of forty-three for alpha, four of forty for the shared point, and three of forty-three for beta.

These fractions are large only because the toy field has forty-three elements. In general, adding the three stages gives a bound on the cheater's chance. The numerator is the number of claims minus one, plus the number of coefficients minus one plus the number of distinct points, plus the number of polynomials. The denominator is the size of the field. In the running example the number of polynomials equals the number of claims, and we'll see claims that share a polynomial shortly.

The toy example fits inside each term. The bound allows two bad values of alpha, six of the shared point, and three of beta, against the one, four, and three we found. The first two counts are smaller because only one claim is false, which leaves a single pole and a combined error of degree one in alpha.

For two to the thirteen coefficients, with the six claims, four points, and four polynomials from the start of this chapter, the numerator comes to eight thousand two hundred four. For a field of about two to the two hundred fifty-four elements, as with the Pasta curves, the bound falls below two to the minus two hundred forty. Ragu draws beta from a shorter, one hundred forty-three bit range, for reasons the chapter on endoscalars explains. With that range, the beta term alone is about two to the minus one hundred forty-one, and it dominates the sum.

Fiat-Shamir lets a cheater retry privately, so the chance grows with the number of attempts, as the chapter on statements and challenges explains. We make no claim here about Ragu's overall security level.

Each challenge follows its message.

All of these counts assume the cheater doesn't know a challenge when it sends the message that the challenge tests. The protocol fails if any challenge arrives early, and each of the three challenges shows this.

Return to the variant in which the first two claims both use the point nine. Suppose the cheater learns alpha equal to eleven before it makes its claims there. It claims thirty-eight for the first polynomial and thirty-nine for the second. Both claims are false, but their errors are chosen so that the weighted combined error vanishes modulo forty-three. The weighted combination is then divisible by X minus nine, which gives a genuine polynomial f. Here the shared point only has to avoid nine, and this cheater passes for all forty-two shared points and all forty-three values of beta, a total of one thousand eight hundred six of one thousand eight hundred six runs.

Next, suppose the cheater learns the shared point seventeen before it commits. The interpolated polynomial from earlier matches the formula at that point, so the cheater commits to it, reports true values, and passes for all forty-three values of beta.

Finally, suppose the cheater learns beta equal to twenty-three before sending its values at seventeen. It sends thirty-eight for the second polynomial, a shift of twenty-seven, which it solves from the one linear equation that makes the total error vanish at this beta. The check passes. Moving to beta equal to twenty-four makes the same message fail.

Binding at the end.

The check on the output claim means something only because the combined commitment can be opened in one way. Every polynomial so far was fixed by its commitment, and a prover who knows a relation among the generators loses that restriction. Using the known discrete logs of the toy generators, a prover can adjust the first two entries of the combined polynomial, giving twenty-six, forty-one, twenty-nine, eight. The new list commits to the same point but evaluates to thirty-three at seventeen, not thirty-two. A prover with this ability could satisfy the final check for a wrong value, which is why the discrete log relation assumption is necessary.

Claims that share a polynomial or point.

The running example gave each claim its own polynomial, while the list at the start of this chapter had two claims each about two of its polynomials. The protocol needs only a small change for this. The prover's value at the shared point depends on the polynomial and not on the original point, so it sends one value per polynomial, and each claim about that polynomial reuses the value. As a result, the formula for f's value still has one term per claim, whereas the combined polynomial has one term per polynomial. This is why six claims need only four values.

Here is an example. Add a fourth claim, that the first polynomial has the value twelve at the point two. This claim reuses the first polynomial, and it also shares the point two with the third claim. The polynomial f gains one term, with the new quotient at the bottom of the weights, and its commitment changes. The prover still sends only the three values fourteen, eleven, and one, because both claims about the first polynomial use the same fourteen. The verifier now derives thirty-two for f's value, the output value at beta equal to twenty-three is twenty-eight, and opening the combined polynomial confirms both the output commitment and that value.

Two claims may also share a point, as the third and fourth claims do here. The verifier then needs only one inverse for that point, and the alpha weights keep the claims apart. Two claims about the same polynomial at the same point with different values can't both be true, and the code rejects such a list before batching.

Here the Ragu Book and the code differ again. The book notes that only one evaluation per polynomial is needed, but its formulas for the combined polynomial and value still index the powers of beta by claim. The prover at the commit this site pins loops over polynomials, so each polynomial appears once in the combination. This is reconstructed from the code, and the authors have not confirmed it. This site follows the code.

With one value per polynomial, we can count what batching saves on the list from the start of the chapter. Take two to the thirteen coefficients and thirty-two byte values. Six separate arguments carry one hundred fifty-six group elements, or four thousand nine hundred ninety-two bytes. One batched argument carries twenty-six group elements, plus the commitment to f and one value for each of the four polynomials, for nine hundred ninety-two bytes. Both counts leave out the small constant number of extra values that each argument carries.

The verifier saves work as well. Its largest cost in each argument is one multi-scalar multiplication over all the generators. Six separate arguments need six of them, while the batched argument needs one, plus a linear combination of five points to form the combined commitment. The last weight is one, so only four of those points need a scalar multiplication.

Blinding factors.

The book's protocol uses hiding commitments, so each commitment and the commitment to f carry blinding factors. Blinding factors combine with the same weights as the polynomials, as the commitments chapter showed. The prover therefore computes the combined blinding factor from those weights, and the verifier's formula for the commitment doesn't change in form.

The toy curve confirms this. With blinding factors seventeen, twenty-nine, and eleven for the three polynomials and five for f, the verifier combines the blinded commitments into one point. The weights give a combined blinding factor of twenty-nine, and committing to the combined polynomial with it gives the same point the verifier computed.

The warning from the commitments chapter applies here as well. At the commit this site pins, the inner product argument code omits this term, and the fuse step commits to f with no blinding factor.

Relation to Shplonk and Halo two.

The Ragu Book credits this technique to Shplonk, a paper by Boneh, Drake, Fisch, and Gabizon. That paper works with KZG commitments and lets the prover open each polynomial at a set of points. Its prover commits to a random combination of fractions, one per polynomial. Each numerator is the polynomial minus its claimed values, and each denominator vanishes on the claimed points. When every set holds a single point, each fraction is one of ours, and the committed polynomial is our f with the weights in a different order.

The two protocols then differ in how they finish. Shplonk's verifier picks a random point and does not receive the polynomials' values there. Instead it uses one more polynomial. For each claim, take the polynomial minus its claimed value, divide by the difference between the random point and the claim's point, and weight it as before. Then subtract f from the sum. By the formula for f's value, this polynomial is zero at the random point when every claim is true.

Once the random point is fixed, each of those divisors is a number, so the new polynomial is a linear combination of the claimed polynomials, the constant claimed values, and f. A constant polynomial commits to that constant times the first generator. So the verifier can build the new polynomial's commitment from the input commitments, the commitment to f, and one multiple of the first generator that collects all the claimed values. The prover then opens the new polynomial at the random point to the value zero.

Ragu instead has the prover send the values and combines them under beta, which matches the multipoint opening in Halo two. Halo two also groups polynomials by their sets of query points and interpolates over each set, whereas Ragu gives every claim its own term. This comparison follows a walkthrough of the paper and the documentation of the gnark crypto implementation. Neither the Ragu Book nor the code explains why Ragu sends the values.

Batching in Ragu.

The clearest place to see this protocol in the code is the compression path, whose module comment describes the same steps. The prover divides without using the claimed value, as we predicted. It then writes the commitment to f, squeezes the shared point, writes the values, and squeezes beta.

The verifier computes f's value and the combined value with two loops, using Horner's rule. That rule builds a weighted sum by repeatedly multiplying the running total by the challenge and adding the next term, which is how the weights arise. Each pass through the first loop multiplies everything so far by alpha and adds the next claim's term, so the first claim ends up with the highest power. The second loop starts from f's value and folds in each polynomial's value with beta, so f gets the highest power of beta. Each claim in that first loop looks up its polynomial's value by index, which is how claims share a polynomial.

The next point is reconstructed from the code, and the authors have not confirmed it. The fuse step runs the same reduction with the same weights, spread across several files, with the verifier's arithmetic in a circuit. It differs from our description in two ways that later chapters cover. The values at the shared point go into a committed stage rather than being sent directly, which is the subject of the chapter on staging. And beta is derived from a one hundred forty-three bit endoscalar rather than taken as a full field element, which is the subject of the chapter on endoscalars.

The chapter on split accumulation wraps this protocol so that the output triple becomes a running accumulator, and the chapter on curve cycles divides its arithmetic between two circuits. We stop before both, since each depends on recursion, which we haven't reached.

Where this leaves us.

A claim holds exactly when the polynomial minus the value is divisible by X minus the point, so a true claim has a quotient and a false one doesn't. The verifier can compute a quotient's value at a new point from the polynomial's value there, which moves the claim to that point. Alpha batching commits to one combination of all the quotients, with random weights that stop errors at a shared original point from cancelling.

The prover then sends one value per polynomial at a random shared point, and the verifier derives f's value from those values and the original claims. Beta batching combines f and the polynomials at that point into one triple, and every input needs a distinct weight. A false claim survives only if a challenge lands on one of a small number of bad values, provided that each challenge comes after the message it tests.

Together with the inner product argument, this gives a single short opening for all of a proof's evaluation claims. The next chapter assembles the arithmetization, the polynomial encoding, the commitments, and this batching into one complete proof.
