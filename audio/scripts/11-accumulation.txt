Chapter eleven. Accumulation.

The chapter on recursive proofs set the goal of a proof that verifies an earlier proof, and a verifier with linear steps blocks that goal. Chapter nine identified the two linear steps in our verifier. This chapter removes one of them, the multi-scalar multiplication that computes a single point at the end of the inner product argument. Chapter seven called that point the final generator or the folded generator, and this chapter uses the second name, because the prover gets it by folding the generators.

The technique does not make that computation cheaper. It postpones the computation, and it lets many postponed computations collapse into one. A prover states the output as a claim, each recursive step merges the new claim with the old one using a random spot check, and one party does the expensive work once, at the very end. The technique comes from Halo, and Bunz, Chiesa, Mishra and Spooner later gave it foundations under the name accumulation scheme.

The merge protocol in most of this chapter is reconstructed from the Ragu Book, the Halo two book and papers, and the authors have not confirmed it. This site rebuilt it from those books, not from code, together with the argument in chapter seven, and a script checked its algebra. It teaches the idea, and it may differ in detail from the protocols in the two papers, of which the site could read only the abstracts. Only the section on accumulation in Ragu rests on the code, at the commit this site pins.

This chapter says that claims merge, following the book's wording for Halo. A merge combines two claims into one. It is a different thing from a fuse, the proof-carrying data operation from chapter two, although a fuse would contain merges if a system used this technique.

The step that remains.

Recall the final check of the inner product argument. Its left side adds each round's two weighted cross terms to the statement point, which takes two scalar multiplications per round. Its right side needs a value from a polynomial with one factor per round, so that value takes about one field multiplication per round. Only the folded generator costs a linear amount, because computing it takes one multi-scalar multiplication over all the generators.

Chapter seven also showed what this point is. The coefficients of that product polynomial are the weights on the generators, so the folded generator is the Pedersen commitment to the polynomial. The polynomial depends on the list of round challenges, so we'll call it the challenge polynomial. Each round contributes one factor, the inverse of that round's challenge plus the challenge times a power of X.

Two features of this polynomial make accumulation possible. It has a description of only one scalar per round, even though it has one coefficient per generator, so anyone can evaluate it at a point with logarithmic work. The commitment is also linearly homomorphic, as chapter six showed, so a combination of such points commits to the same combination of polynomials. The sections below use both.

Splitting off the expensive step.

The verifier needs the folded generator only as an input to one equation, so it can test that equation with a value somebody else computed. Let the prover supply the point. The verifier then does all the logarithmic work, runs the final check with the supplied point, and stops short of the multi-scalar multiplication.

What it has left is one unverified statement, which we call a claim. A claim is a pair made of the supplied point and the list of round challenges, and it says that this point really is the commitment to the challenge polynomial. The verifier's conclusion now has a condition attached, because the evaluation claim holds provided that this statement is true. The claim is small, at one point and one scalar per round, even though it speaks about all the generators.

On the run of chapter seven, whose round challenges are fifteen and ten, the prover sends the folded generator along with the proof. The verifier evaluates the challenge polynomial at nine to get nineteen, the final check passes with the supplied point, and the verifier outputs the claim.

The condition matters, because a prover who chooses that point has real power over the final check. As the recursive proofs chapter showed, such a prover can solve the final equation for the point it supplies. Here is that attack on the run of chapter seven, which later sections reuse.

Take the false value thirty-eight from chapter seven, where the true value is thirty-seven. The statement point now carries one extra copy of U, and honest folding keeps it, so with the true folded generator the final check fails. The prover keeps the final scalar four, and eleven is the inverse of four modulo forty-three. So it adds eleven copies of U to the point it supplies, and the right side picks up exactly the one extra U it needed. The check passes, and only the claim is wrong.

So a passing final check proves nothing unless somebody eventually confirms the claim. The rest of the chapter arranges for that confirmation to happen once, however many claims arise.

Deciding a claim.

The direct way to confirm a claim is to run the postponed computation. Multiply out the factors of the challenge polynomial, compute the multi-scalar multiplication, and compare the result with the supplied point. We call the party who does this the decider, and we call the check itself deciding.

For the true claim from chapter seven, the two factors multiply out to four coefficients, forty-one, fifteen, twenty-three and twenty-one. The multi-scalar multiplication with the generators gives back the supplied point, so the decider accepts. For the forged claim, the same computation gives the same honest point, which differs from the forged one, so the decider rejects.

Moving this computation out of the verifier helps a recursive proof, because the decider runs outside any circuit. It does not reduce the total work, though. A chain of recursive proofs creates a new claim at every step, and each one would have to be carried in the statement until a decider dealt with it.

With eight thousand one hundred ninety-two generators and a hypothetical one thousand steps, checking every claim directly takes one thousand multi-scalar multiplications. That comes to eight million one hundred ninety-two thousand scalar multiplications. The statement would also carry one thousand points and thirteen thousand challenges.

The statement must stay a fixed size for recursion to work. So we need to turn several claims into one claim, cheaply enough to do inside a circuit.

Testing a claim at one point.

We start with one claim and look for a test cheaper than the multi-scalar multiplication. The claim says that a point commits to a particular polynomial, and the earlier chapters already show how to query a committed polynomial. The verifier can pick a random point, ask the prover to open the supplied point there using an inner product argument, and compare the opened value with the challenge polynomial's value.

The verifier can make that comparison because the product form takes only logarithmic work, however many generators there are. Take the claim from chapter seven and the point twenty-nine. The two factors of the challenge polynomial come to thirty-nine and two there, and their product is thirty-five. Evaluating the four coefficients directly gives thirty-five as well, but that route needs every coefficient, while the factors need only one term per round.

The test catches a false claim for the reason chapter three gave. Suppose the point actually commits to some other polynomial whose degree is below the number of generators. A point that also hides a multiple of U is a separate case, which later sections handle. The difference between the two polynomials is then nonzero, with fewer roots than there are generators. So the opened value matches at only those few roots, out of the whole field, provided the prover fixes its point before it learns the test point.

Here is an example. Suppose a claim's point commits to a false polynomial, which we chose so that its difference from the true one is a cubic with as many roots as a cubic can have. Testing all forty-three points, the two agree at two, seven and twenty and nowhere else. So the spot check catches this claim at forty of the forty-three points.

This opening differs from the openings of earlier chapters in two ways. First, its witness is public. The list being opened is the challenge polynomial's coefficient list, which anyone can compute from the round challenges, so the prover needs no secret and no stored data to run this argument. It pays a linear cost to multiply out the factors and fold, but it does this outside the circuit.

Second, this opening is itself an inner product argument, so its verifier faces its own final check with its own folded generator. Splitting that check produces a new claim. For a single claim, we have therefore traded one claim for another plus some logarithmic work, and that looks like no progress. The gain appears when two claims share one opening.

Merging two claims.

Suppose we hold two claims, and we would like one opening to test both. A random linear combination from chapter three can do this. So take a challenge called alpha, and add the first claim's point to alpha times the second claim's point. We'll call the result the merged commitment.

If both claims are true, homomorphism tells us what this point commits to. Each input point commits to a coefficient list, so the merged commitment commits to the first list plus alpha times the second. That is the first challenge polynomial plus alpha times the second.

We want to open this commitment at a random point, which we'll call the merge point. Chapter seven proves openings of a particular form, an inner product of the committed list with the list of powers of the point. So the witness is the combined coefficient list, the first plus alpha times the second, and the prover can compute it from the public challenges.

Its inner product with the powers splits along the sum, and each piece is one challenge polynomial evaluated at the merge point. The verifier holds both sets of round challenges, so it can compute that sum through the product forms with logarithmic work. We call the result the merged value.

The statement to prove is now an ordinary evaluation claim, that the merged commitment opens at the merge point to the merged value. The verifier computed every part of that statement from the two input claims.

Each challenge has a separate job. The merge point exposes a wrong polynomial, as in the last section. The weight alpha stops two wrong polynomials from cancelling each other. Without it, a prover could make the first polynomial too large by some amount and the second too small by the same amount, and the sum would be correct at every point.

The argument needs one more ingredient, which chapter seven introduced. The input points come from the prover, so they could contain a hidden multiple of U. Suppose the first point commits to its challenge polynomial plus some constant, and also hides that constant times U.

Then the merged commitment commits to a polynomial whose value at every merge point exceeds the merged value by that constant. Once the verifier adds the merged value times U, the hidden term supplies exactly the missing part of the value. No choice of merge point or alpha exposes this.

We therefore weight U by a third challenge called tau, sampled after the input points, and we use tau times U as the value generator in every round. The hidden term is still the constant times U, while the value now needs tau times the constant times U. So the two match only when tau is one. The statement point for the argument is the merged commitment plus tau times the merged value times U.

The prover now runs the inner product argument of chapter seven on the witness list with fresh round challenges, and the verifier splits off the final check as before. The new challenge polynomial, built from those fresh challenges, gives the value that the final check uses. The result is one claim, made of the new supplied point and the fresh challenges, with the same form as each input.

The order of messages keeps the prover from choosing anything after it sees the challenge that tests it. The verifier sends the merge point, alpha and tau first. In each round the prover then sends two cross terms and the verifier replies with a round challenge. The prover finishes with the final scalar and the supplied point.

The same construction handles any number of claims, using successive powers of alpha as the weights on the points and on the values. The verifier's work grows by one scalar multiplication and one factor multiplication per round for each extra claim.

A complete merge on the toy curve.

We need two claims to merge. The first comes from the run in chapter seven, which opened its polynomial at nine with round challenges fifteen and ten. The second comes from a fresh run on chapter six's other list, opened at five with round challenges three and five. Both runs use chapter seven's fixed U, and all challenges are picked by hand.

Both final checks pass, so the verifier holds two claims and has not yet done any linear work.

The verifier now sends the merge point twenty-nine and alpha equal to sixteen. The two challenge polynomials evaluate to thirty-five and twenty-eight there. So the merged value is thirty-five plus sixteen times twenty-eight, which is ten modulo forty-three. The verifier also computes the merged commitment from the two input points.

Meanwhile the prover multiplies out both challenge polynomials from the public round challenges, and combines the two coefficient lists with weight sixteen. Committing to the combined list directly gives the merged commitment, and evaluating it at twenty-nine gives ten, so the claim is true.

The verifier then sends tau equal to twenty-two. Both sides form the statement point, which is the merged commitment plus five copies of U, since tau times ten is five. The rounds use tau times U as the value generator.

The rest is the inner product argument on the combined list, even though nothing about it is secret here. The prover folds, and the verifier updates the statement point after each round, with round challenges eight and twelve. A few points in this run repeat earlier points, which means nothing, because the toy group has only forty-three elements.

The prover sends the final scalar seventeen and supplies a point. The verifier evaluates the new challenge polynomial at twenty-nine, which gives two. Both sides of the final check come out as the same point, so the verifier accepts and outputs a single claim.

The point that an honest prover gets by folding the generators is the commitment to the new challenge polynomial, because the folding depends only on the round challenges and never on the list being opened. The verifier never computes this point, but the decider does. Suppose this is the last claim, so a decider takes over.

The decider multiplies out the new polynomial, computes one multi-scalar multiplication, gets the supplied point, and accepts. That one computation is the only linear group work outside the prover. We can also check what it vouches for by running the two computations it replaced, and they do give the two input points.

Keeping a running accumulator.

A merge turns two claims into one claim of the same form, so we can repeat it. We call the object that carries the current claim forward the accumulator. Each step produces one new claim from the proof it just verified, and merges that claim into the accumulator.

The first step has no earlier accumulator, which is one of the base cases that the recursive proofs chapter handles. In this scheme, the first step can merge with a fixed placeholder claim whose point anyone can compute once in advance. One choice is the claim with every round challenge equal to one. Its polynomial has every coefficient equal to one, so its point is the sum of the generators.

On the toy curve, merging that placeholder with the first claim, using the same challenges as before, gives a merged value of twenty. The final check passes, and the decider accepts the output claim. The placeholder behaves like any other true claim.

Continuing the toy run, two more claims each come from a fresh inner product argument on a new polynomial. The accumulator absorbs the third claim with a merge point of twenty-one, and then the fourth with a merge point of twenty-six. The decider computes one multi-scalar multiplication for the last accumulator and accepts. That single check covers all four input claims.

One recursive step.

Here is how this fits inside the step that the previous chapter describes. The previous proof's statement contains the accumulator, and the step's circuit does four things. First, it runs the previous proof's verifier up to the split, which yields a new claim from the previous proof's own inner product argument. That verifier still computes the wiring polynomial's value, the other linear step from chapter nine.

Second, it derives the merge point, alpha and tau from a transcript that contains the accumulator and the new claim, and it computes the merged commitment and value. Third, it checks the merge's inner product argument up to the split, using a merge proof that the prover computed outside the circuit and supplied as a witness. Fourth, it places the resulting claim in its own statement as the next accumulator.

The last three of these take logarithmic work, and so does the inner product part of the first. The wiring polynomial's value is still linear in the circuit size, because accumulating the folded generator does nothing for it, and a later section returns to it.

What accumulation does guarantee is that none of the circuit's work depends on how many steps came before, because the accumulator stays one point and one challenge per round. Once a step has proved the merge check, later steps have no use for the old merge proof. The curve's points also do not live in the circuit's field, a problem the curve cycles chapter deals with and we ignore here.

Proof-carrying data has a tree in place of a chain, so a step with two children holds two accumulators and two new claims. The powers of alpha cover this case. As an example, merge the first, second and fourth claims in one step.

In a real run the transcript would absorb all three claims, so the challenges would differ. We reuse the earlier challenges here so that the two runs can be compared. The merge gives a merged value of seventeen, the final check passes, and the output point is the same as in the two-claim merge.

The output point is the folded generator, which depends only on the new round challenges. The inputs enter through the merged commitment, the merged value, the cross terms and the final scalar, and all four of these change when a claim is added.

What each party pays.

The verifier's side of a merge is now small, and the prover takes on the linear work. Take one merge of two claims, with eight thousand one hundred ninety-two generators. The verifier spends one scalar multiplication on the merged commitment, twenty-six on the cross terms, and two on the final check, which makes twenty-nine. Evaluating the three challenge polynomials costs it only a few dozen field operations.

That count of two for the final check assumes the verifier never forms the statement point separately. It moves the tau term to the right side of the final check, where it combines with the other multiple of U.

The prover spends about sixteen thousand three hundred eighty-four field multiplications to multiply out the two input polynomials. It then spends thirty-two thousand seven hundred sixty-four scalar multiplications on the cross terms and on folding the generators, as the list halves in each round.

Over the same hypothetical one thousand claims, the group work that a verifier must do drops from eight million one hundred ninety-two thousand scalar multiplications. It becomes twenty-nine per merge, plus one decider computation of eight thousand one hundred ninety-two. The accumulator stays at one point and thirteen challenges, or four hundred forty-eight bytes. Each merge proof holds twenty-six points and one scalar, or eight hundred sixty-four bytes.

Deciding needs no help from the prover. Anyone who holds the final accumulator and the public generators can run it, and the Halo two book describes this as one linear-time computation that settles an entire batch.

What the final verifier does.

The chain ends with a last proof, which a verifier outside any circuit receives. Its statement contains the accumulator, which covers every claim up to the previous step. The last proof also has its own inner product argument, and splitting that argument's final check produces one more claim that no step has merged yet.

The final verifier therefore has two claims in hand, and it has two ways to finish. It can decide both claims, which takes two multi-scalar multiplications. Or the prover can send a merge proof for the two claims along with the last proof, computed outside any circuit as usual. The verifier then checks that merge and decides the single result.

On the toy chain, suppose the chain stops after the fourth claim, and treat that claim as the last proof's own claim. The last proof's statement carries the accumulator covering the first three claims. The final verifier splits the last proof's argument to get the fourth claim, checks the merge proof, and decides the one result.

With eight thousand one hundred ninety-two generators, this costs twenty-eight scalar multiplications for the split, twenty-nine for the merge and eight thousand one hundred ninety-two for the decider. That comes to eight thousand two hundred forty-nine in all.

Deciding the accumulator and the last claim separately needs no merge proof. But it still needs the twenty-eight for the split and then two multi-scalar multiplications, or sixteen thousand four hundred twelve scalar multiplications. Either way, a constant number of multi-scalar multiplications settles the whole chain, and with the extra merge proof the count stays at one.

Why cheating fails.

Nothing inside the chain runs the multi-scalar multiplication, so we need to see why a false claim cannot disappear along the way. A cheater wants some input claim to be false while the final accumulator is true.

We start with something the accumulation verifier cannot do. The merge ends in a final check with a supplied point, just like the check in the split. We saw that a prover can make such a check pass by adding a suitable multiple of U to the point it supplies. That trick works whatever went wrong earlier in the merge, so the accumulation verifier on its own never stops a prover who is determined to continue.

The guarantee that a merge does give is narrower. If any input claim is false, then the output claim is false as well, except at a few unlucky challenges. The counts below measure that luck. When we say that a merge passes, we mean that it passes with the honest output point, the one the prover gets by folding the generators, so that the output claim is true. Every other way through the final check leaves a false output claim for the decider.

The counts also need a model of a real curve. On the toy curve every point is a known multiple of every other, so a cheater could solve for a forgery at almost any challenge, as chapter seven showed. The script therefore also runs the protocol in a formal group, where each point is a list of its coefficients on the generators and U. Two points there are equal only if the lists are.

A false claim moves forward.

The first case shows the forged output at work. Take the forged claim from the split, whose point hides eleven copies of U, and merge it with the true second claim, using the same challenges as before. The honest fold reaches the honest output point, but the final check fails.

The script repeats this in the formal group for all one thousand eight hundred six pairs of merge point and alpha, and five values of tau, with no acceptances. To continue, the prover has to repeat its trick and add thirty-one copies of U to the output point. That passes the final check, so the false claim has moved to the output. The decider then computes the honest point, sees the difference, and rejects.

A false input.

Next we count how often a false input yields a true output. Take the case where the prover holds a real polynomial behind a wrong point, and folds honestly from then on. Use the false polynomial with three roots from earlier, and merge it with the true second claim.

For each of the one thousand eight hundred six pairs of merge point and nonzero alpha, run the merge with the prover folding its real list and supplying its honest folded generator. The check passes for one hundred twenty-six pairs. These are exactly the pairs whose merge point is two, seven or twenty, the roots of the difference. Alpha plays no part, because only one input is wrong.

Two false inputs.

With two false inputs there is a chance that the errors cancel, which is the case that alpha exists to handle. Now make the second claim false as well, with its own error polynomial. A pair passes when the first error at the merge point, plus alpha times the second error there, comes to zero.

Running all one thousand eight hundred six pairs gives thirty-nine that pass. The multivariate root count from chapter three bounds this at four times forty-three, or one hundred seventy-two, since the expression has total degree at most four.

To see what alpha prevents, let the second error be the exact negative of the first. With alpha fixed at one, the errors cancel, and all forty-three merge points pass. With alpha random, one hundred sixty-six pairs pass, which are those forty-three pairs with alpha equal to one and the pairs at the three roots. For a real curve the same reasoning gives a bound of the number of generators divided by the field size, which is negligible.

What the decider settles.

A false claim therefore survives from merge to merge, and at each merge it has a small chance of turning into a true one through a lucky merge point. If it survives to the end, it meets the decider, which computes the multi-scalar multiplication and catches it. This is the sense in which one decider check covers everything before it.

A true final accumulator means that, except with small probability at each merge, every input claim was true too. A verifier who skips the decider has no such assurance, because every step before the decider may be carrying a false claim.

The prover could also send altered cross terms in the merge, instead of folding honestly. Chapter seven's gap argument covers this, and it allows at most four surviving challenges per round. On the toy curve that fraction is large, but on a real curve it is negligible.

The order of the messages.

The bound on false inputs depends on the prover fixing its points before it sees the merge point. Suppose the prover learns the merge point twenty-nine before it fixes its point. It picks the true polynomial plus five times a factor that vanishes at twenty-nine, and it sends the commitment to that, which is not the true point.

The two polynomials agree at twenty-nine, so the merge passes, and every later step is honest. If instead the point is fixed first and the merge point varies over all forty-three values, the merge passes only at twenty-nine.

In a non-interactive proof, this means that the transcript has to absorb both input claims in full before it produces the merge point, alpha and tau, for the reason chapter three gave. The round challenges belong to the claim as much as the point does. A prover who could change them after the merge point was fixed could change the polynomial that the check compares against.

The weight on U.

A prover can also hide a multiple of U in an input point, and arrange the generator part and the U part of the point to offset each other at every merge point at once. Take the first claim's point plus six copies of the first generator and six copies of U. The prover then holds the true polynomial plus six, and the hidden six copies of U pay for the extra value.

With tau fixed at one, the merge passes for all one thousand eight hundred six pairs of merge point and alpha, although the claim is false. At our merge point and alpha, trying all forty-two nonzero values of tau gives acceptance at one only.

The merge has to reject this point whatever produced it, because the chain's guarantee is that a passing merge implies true inputs. The inner product argument alone cannot do this, for the reason chapter seven gives. Its gap argument proves only that the statement point has the form of some list committed on the generators, plus that list's inner product times U.

That relation matches the evaluation claim only when the commitment has no U component, and here the merged commitment carries whatever U part the input points carry. The random weight tau closes this gap in the same way as the extra challenge on U in chapter seven.

Assumptions.

This reasoning is informal and is not a security proof. It relies on the discrete log relation assumption for the generators together with U. It assumes that the prover builds its points from the generators with coefficients it knows. It assumes that challenges are uniform and come after the data they test, which in a non-interactive proof means treating the transcript hash as a random oracle. Finally, it assumes that the decider runs honestly on the final accumulator.

Recursion adds a further layer that we have not analysed, because each step's statement relies on proofs that themselves rely on earlier proofs. The abstract of the accumulation scheme paper notes that Halo's authors outlined their approach without details or security proofs, and it presents foundations for that approach as the paper's purpose.

Atomic accumulation.

We can now give the general pattern a name. An accumulation scheme has three parts. The accumulation prover produces a new accumulator and a proof that it was formed correctly. The accumulation verifier checks the update cheaply. The decider checks the final accumulator, possibly at great expense.

The scheme in this chapter has a special property, which is that the accumulator is all that anybody needs. The polynomial behind a claim can be rebuilt from its round challenges, so neither the prover of the next merge nor the decider needs extra data. The book calls this form atomic accumulation. It describes this as the original formalization, in which the accumulator alone lets a party produce and check each insertion.

The atomic form has a cost that explains why later work moved on from it. Every proof placed into an atomic accumulator has to be partly verified inside the circuit, so that proof must already be short and its verifier sublinear, apart from the deferred part. In our setting, that means a full inner product argument for each proof at every step, and then one more for the merge. That puts this linear work on the prover of every step.

The next chapter relaxes this by letting the accumulator have a separate witness that only the prover and the decider hold. That permits a long proof with no inner product argument during recursion, and it is the form that Ragu uses.

The other linear step.

Chapter nine listed two linear steps, and so far we have dealt only with the folded generator, which is why the recursive step still contains a linear computation. The other is computing the wiring polynomial's value, which requires reading the whole circuit. Our spot check relies on the challenge polynomial having a short product form, and the wiring polynomial has none. The verifier cannot evaluate it cheaply at a random point, so the spot check does not carry over directly.

The Ragu Book describes how Halo handled this case. The prover supplies a claimed commitment to the wiring polynomial, and a parallel protocol reduces such claims together by random spot validation. Ragu has its own treatment in the chapter on wiring and the registry, so we leave the details to that chapter.

Accumulation in Ragu.

The code, at the commit this site pins, contains the exact objects of this chapter. It has a type called accumulator with two fields, a point and a list of challenges. The point is our folded generator, and the challenges follow the one-sided convention of chapter seven, in which each factor is one plus the challenge times a power of X.

One method on the verifier's guard, called use g, is the split, since it takes a supplied point and returns this type. Another, called use challenges, is the direct route, which adds the whole list to the multi-scalar multiplication.

The following is reconstructed from the code at the commit this site pins, and the authors have not confirmed it. First, the deferral is not in use. The site's search finds use g and a method called compute g called only from one test of the inner product argument, and it found no code that merges two such accumulators. The inner product argument runs at compression, and the compression verifier calls use challenges, so it computes the full multi-scalar multiplication.

Second, Ragu accumulates something else. The fuse accumulates a polynomial with a claim about its value at one evaluation point, which is a batched evaluation claim of the form in chapter eight. The proof keeps the polynomial itself. That is split accumulation, the subject of the next chapter. The same file has a private type also named accumulator, which is unrelated to the type above.

Third, the aggregator profile foresees circuits that verify a compressed proof, and those circuits would face this same computation. They have not landed, and the site found nothing that says whether they would use the split, so this remains unsettled.

The book and the code describe this differently. The book's appendix on snarks says that the instance of the non-interactive argument contains the accumulator state of the inner product argument. Its comparison table lists that verification as linear time, deferred via accumulation.

In the code at the pinned commit, a proof's accumulated state is a batched polynomial claim and not a point with its challenges, and the inner product argument's multi-scalar multiplication runs in full at compression. The code's comment on the accumulator type also calls it an evaluation claim and a proof, while its fields are one point and the challenges.

This site follows the code. The book's general statement that Ragu's scheme descends from Halo's is consistent with both, since the next chapter builds directly on these ideas.

Names differ across sources as well. The book and the code each name the folded generator differently from this site. The Halo two book also writes its factors with the inverse in the other place, so compare the placement of the inverse and the order of the rounds before you move a formula between sources.

Where this chapter leaves us.

The verifier can take the folded generator from the prover and finish with logarithmic work, which leaves a claim that a decider can confirm with one multi-scalar multiplication. A random spot check tests a claim, and a random combination of two claims becomes one evaluation claim with a public witness. Proving it yields a single new claim.

Repeating this keeps one fixed-size accumulator across any number of steps, and the final verifier runs one multi-scalar multiplication as the decider. A false input passes only at rare challenges and otherwise forces a false output, so the chain establishes nothing until the decider has run. Ragu's code contains the claim type, but its recursion uses a different form.

Atomic accumulation still runs a complete inner product argument at every step. The next chapter separates each accumulator into a public instance and a private witness. That removes the argument from the recursive path and lets the steps use a proof without any succinctness at all.
