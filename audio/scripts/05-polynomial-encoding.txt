Chapter five. QAP and Polynomial Encoding.

The last chapter ended with two ways to write the same statement, a list of R one C S rows and Ragu's single consolidated equation. Neither form helps the verifier yet, because checking either one means looking at the whole witness. This chapter turns those equations into statements about polynomials, which a verifier can test at a single random point.

There are two routes, and we take them in order. The first is the quadratic arithmetic program, or QAP, the standard reduction behind systems such as Groth sixteen. It ends in a divisibility test with a quotient polynomial. The second is the route Ragu takes, which reads the claim from one coefficient of a product and needs no division.

Ragu uses this second encoding where it needs a short proof. The chapter on the complete proof also shows a cheaper check that gives up short proofs, and the comparison near the end of this chapter explains when Ragu uses each. We run both routes on the same statement as before, x cubed plus x plus five equals thirty-five, modulo forty-three, the scalar field of the toy curve that the next chapter builds. Apart from a sketch of Groth sixteen, no curve points appear here.

What polynomials provide.

Suppose two polynomials of degree at most some bound differ. Their difference is a nonzero polynomial of at most that degree, so it has at most that many roots, and the two polynomials agree on at most that many points. This is the one-variable case of the Schwartz-Zippel lemma from the chapter on statements and challenges. So a check at one random point says something about every coefficient at once.

To use this fact, we have to express the claim that all the constraints hold as an equality of polynomials. A QAP assigns each constraint row to its own point of the field, so a true statement makes a polynomial vanish at all of those points. Ragu has already merged its constraints into one scalar equation, so it only has to place that scalar where a verifier can reach it.

Both routes also need a way for the verifier to learn the value of a polynomial it does not hold. In a deployed system this comes from a polynomial commitment, which the next chapter builds. To keep the reasoning separate from the cryptography, we pretend for now that the verifier has an oracle for each polynomial the prover sends.

An oracle is a black box that fixes a polynomial at the moment the prover sends it. Afterward it answers any question of the form, what is the value at this point? The verifier never sees the coefficients, and the prover cannot change the polynomial once sent. A protocol written this way is called a polynomial interactive oracle proof, or polynomial I O P.

Each oracle also has a degree bound, agreed in advance, and it refuses any polynomial above that degree. The bound is what makes root counting useful, because the argument above only limits the number of roots when the degree is limited.

An example shows what goes wrong without a bound. Modulo forty-three, take X to the forty-two, minus one. By Fermat's little theorem, this polynomial is zero at all forty-two nonzero points of the field. If a cheater's error could take this form, a check at a random nonzero point would never see it. With a degree bound of seven, the bound of the toy run later in this chapter, any nonzero polynomial the prover sends is zero at no more than seven of the forty-three points.

The commitment of the next chapter supplies this bound. Its public parameters contain one curve point for each coefficient, so parameters with a given number of points can hold at most that many coefficients. We take this capacity as a premise here, and the next chapter shows where it comes from.

One naming note. In the QAP part of this chapter, x is the secret input, as in the last chapter. Later, the letter x names a random evaluation point instead, so there we speak of the witness with secret input three, and the false witness with secret input four.

The R one C S starting point.

We start from the R one C S form of our statement, built at the end of the last chapter. Its wire list holds the constant one, the public output, the secret input, and two intermediate wires. Three public matrices, which we'll call the left, right, and output matrices, define three rows.

Each row combines the wire list using its row of the left matrix and its row of the right matrix, then multiplies the two results. The product must equal the combination given by the output matrix.

Our wire list is one, thirty-five, three, nine, twenty-seven. The left combinations are three, nine, and thirty-five, and the right combinations are three, three, and one. Multiplying entry by entry gives nine, twenty-seven, and thirty-five, which are exactly the output combinations. A real circuit can have many thousands of rows, and the verifier should not have to examine them one by one.

Interpolating the rows.

We want one polynomial that carries all the rows. A polynomial can store one value at each point of the field, so we give each row its own point. This set of distinct points is called the domain, and our example uses one, two, three.

The most direct idea is to interpolate the left combinations themselves. That polynomial would hold the right values, but nothing about it would show that it came from the left matrix and a real witness. If the prover could hand over any polynomial in its place, it could pick one that satisfies the final test without coming from any witness.

Building the polynomial from fixed pieces that describe the matrix gives a structure to check, namely that the prover's polynomial is a combination of those pieces. An oracle cannot check this structure by itself, because it accepts any polynomial within its degree bound, and the section on Groth sixteen shows how a setup makes it checkable. So we interpolate the matrix alone.

Each column belongs to one wire, so we build one polynomial per column, whose value at each domain point is that column's entry for the matching row. The right and output matrices get column polynomials in the same way. Enough points determine a unique polynomial, so these exist, and they depend only on the circuit.

To construct them, we first build a polynomial for each domain point that equals one there and zero at the others. Multiply together X minus each of the other domain points, which makes it zero at those points. Then divide by the product's value at the chosen point, which scales it to one there. These are the Lagrange basis polynomials.

For the point one, the product is X minus two, times X minus three, and its value at one is two. Dividing by two modulo forty-three means multiplying by twenty-two, and the result is three plus nineteen X plus twenty-two X squared. It equals one at the point one and zero at two and three.

Any column is then a sum of basis polynomials, each weighted by that column's entry for the row. For example, the left matrix's column for the constant wire has entries zero, zero, five, so its polynomial is five times the third basis polynomial. Columns of zeros give the zero polynomial.

Adding the witness.

The column polynomials describe the circuit, so now we bring in the witness. Multiply each column polynomial by its wire value and add. This gives the left, right, and output polynomials.

At a domain point, each column polynomial gives its entry for that row, so the left polynomial equals that row's left combination, and likewise for the others. So each row says that the left polynomial times the right polynomial equals the output polynomial at that row's point. The rows hold exactly when this holds at every domain point. In our example, reading the three polynomials at one, two, and three gives back the combinations from before.

The vanishing polynomial and the quotient.

Define the difference polynomial as the left polynomial times the right, minus the output. The rows hold exactly when the difference is zero at every domain point. That is still one fact per row, and one random point would not capture them, because a random point is almost never in the domain. We need a statement that holds as an identity across the whole field.

The factor theorem provides it. If a polynomial is zero at a point, then X minus that point divides it. Since the domain points are distinct, the difference is zero on the whole domain exactly when the product of all those factors divides it. That product is the vanishing polynomial of the domain.

So the rows hold exactly when some polynomial, called the quotient, times the vanishing polynomial equals the difference. The left and right polynomials have degree at most one less than the row count, so the difference has at most twice that degree. The vanishing polynomial has degree equal to the row count, so the quotient has degree at most two less than the row count.

The column polynomials and the vanishing polynomial together make up the QAP. A witness satisfies the QAP when the quotient exists.

In our example, with three rows, the difference has degree four and nonzero coefficients, yet it is zero at one, two, and three. The vanishing polynomial is X minus one, times X minus two, times X minus three. Long division leaves no remainder and gives the quotient thirty-seven plus thirty-three X, of degree one as predicted.

Testing the identity at one point.

Now we have an equality of polynomials, so our random-point reasoning applies. In oracle form, the prover sends oracles for the left, right, and output polynomials, each with degree bound one less than the row count. It also sends an oracle for the quotient, with degree bound two less than the row count.

The verifier picks a random test point and queries the four oracles there. It computes the vanishing polynomial at that point itself, because the vanishing polynomial is public. Then it compares left times right minus output with the quotient times the vanishing polynomial.

Both sides have degree at most twice one less than the row count. So if they are different polynomials, they agree on at most that many points, and a false identity passes with probability at most that degree divided by the field size.

Take the test point eleven. Left times right minus output comes to twenty-nine. The quotient is thirteen and the vanishing polynomial is thirty-two, and their product is also twenty-nine modulo forty-three. Checking all forty-three possible test points confirms that the honest polynomials pass at every one, as an identity should. So one comparison of field elements has replaced all the rows.

Why a cheater's quotient does not exist.

Keep the public value thirty-five and try the secret input four, which gives the wire list one, thirty-five, four, sixteen, twenty-one. The first two rows hold, and the last gives thirty against thirty-five. The difference built from this witness is zero at one and two, but thirty-eight at three. Division by the vanishing polynomial leaves a nonzero remainder, so no quotient exists.

The reason is that a failing row makes the difference nonzero at that row's point, while any multiple of the vanishing polynomial is zero there. The prover can still send an oracle for some polynomial of degree at most one as its quotient, and hope the test misses.

On the toy field we can count every such attempt. We leave the domain points out, because the vanishing polynomial is zero there and a test at such a point says nothing about the quotient. A real field is so large that a random point lands in the domain with negligible probability.

There are one thousand eight hundred forty-nine candidate quotients, each tried at the forty points outside the domain. Nine hundred nine candidates pass nowhere, one hundred sixty pass at one point, and seven hundred eighty pass at two. None passes at more than two of the forty. Averaged over all candidates, a random guess passes at a rate of one in forty-three.

The degree bound explains the maximum. A guess passes exactly where the difference minus the guess times the vanishing polynomial is zero. That polynomial is nonzero, because the difference is not a multiple of the vanishing polynomial, and it has degree at most four, so it has at most four roots. Two of them are always one and two, inside the domain, whatever guess the prover chooses. That leaves at most two roots outside the domain, which is the maximum in the count.

This argument only works if the oracles are fixed before the verifier picks the test point. Suppose the prover with secret input four learns the point eleven in advance. At eleven, its difference is four and the vanishing polynomial is thirty-two, so it divides to get twenty-seven and presents the constant polynomial twenty-seven as its quotient.

The check at eleven passes, because twenty-seven times thirty-two is four modulo forty-three. At twelve, the same quotient gives twenty-seven against a true value of thirty-three. So the forgery only works at the point the prover knew in advance.

The test also assumes that the three polynomials really are combinations of the column polynomials with one shared witness. If the prover could present any three polynomials, it could set them all to zero, and the identity would hold with a zero quotient for any statement. A plain oracle does not prevent this.

So a complete QAP-based system has to enforce three things. The prover's polynomials must be fixed before the test point is known. Each of the three must be a combination of the column polynomials. And all three must use the same wire list.

Enforcing the test in Groth sixteen.

Groth sixteen enforces these requirements by keeping the test point secret from everyone, including the prover. We just saw why the prover must not know it. So the question becomes how the prover can evaluate its polynomials at a point it does not know.

The answer uses an elliptic curve with a generator point. A setup ceremony picks a secret point, publishes the generator multiplied by each power of that point, and then destroys the secret. The prover multiplies each published point by its matching coefficient and adds the results. Because scalar multiplication distributes over addition, the total is the generator multiplied by the polynomial's value at the secret point.

So the prover gets its polynomial's value hidden inside a curve point, without ever learning the secret, because recovering it is a discrete log problem. The ceremony also publishes points built from the column polynomials at the secret point, together with further secret values. The prover can only form linear combinations of published points. So the extra points restrict it to polynomials of the required form, and the further secret values force one shared witness into all three.

The verifier still has to check a multiplication, left value times right value, while holding both only inside curve points. Adding points cannot multiply the hidden scalars, so Groth sixteen uses a pairing. A pairing maps two curve points to an element of another group, so that scaling the inputs by two scalars raises the output to their product.

Applied to the two hidden values, a pairing puts their product in the exponent, and the verifier compares it against a similar pairing of the other side. Only some curves, called pairing-friendly, have an efficiently computable pairing. The resulting proof is three group elements, and verification uses three pairings. What matters here is the list of things this construction relies on.

The cost of QAP.

Each ingredient of the QAP route has a cost, and several of those costs conflict with what Ragu needs.

First, the prover works over a special domain. Interpolating and multiplying term by term takes time quadratic in the row count, so real provers use the fast Fourier transform. That requires the domain to be a set of roots of unity, which also gives the vanishing polynomial a compact form.

In our field, six cubed is one modulo forty-three, so one, six, and thirty-six form such a domain, and the vanishing polynomial collapses to X cubed minus one. Repeating the construction on this domain gives different polynomials, and the exact quotient eleven plus forty-two X. The same field has no domain of size four, because four does not divide forty-two. So real proof systems pick fields whose multiplicative group has a large power of two in its order.

The product is also larger than the circuit, because it has about twice the degree of its factors, so holding it by its values takes a domain about twice the size. For sixty-five thousand five hundred thirty-six rows, the difference has degree up to one hundred thirty-one thousand seventy, and the next power of two is one hundred thirty-one thousand seventy-two.

Groth sixteen provers avoid the larger domain by working on a shifted copy of the domain, made by multiplying every point by a value outside it. There the vanishing polynomial takes one nonzero value at every point. So the prover gets the quotient at each point by dividing the difference there by that constant. The quotient has degree below the row count, so every transform stays at the original size, though the prover still runs several of them.

Second, the setup requires trust. Anyone who learns the secret point or the other secret values can forge proofs, as our small forgery showed. Groth sixteen also ties its setup to one circuit, because the ceremony publishes points built from that circuit's column polynomials, so a new circuit needs a new ceremony. Ragu's overview sets out to avoid a trusted setup altogether.

Third, the verifier needs pairings, which are what make the secret point usable. Ragu works over the Pasta curves, which are not pairing-friendly, so this check is not available to it.

Fourth, the circuit description has to exist as polynomials. Before any proof, someone has to compute all the column polynomials and, in Groth sixteen, fold them into the setup, once per circuit. That matters for Ragu, because a proof-carrying data tree runs many different small steps, and Ragu splits large computations into many small circuits. The same overview lists the QAP reduction among the things its construction avoids.

So Ragu has to reach a polynomial test some other way. With no secret point and no pairing, its verifier can only use plain oracles with degree bounds, which the commitments of the next chapter provide.

The consolidated equation as a coefficient.

Ragu starts from a different place. A QAP keeps the rows separate until the end and uses the domain to pack them together. Ragu has already combined its gates and constraints using the gate challenge and the constraint challenge, which left one scalar equation in the last chapter.

On the left of that equation is the revdot product of the structured vector with the sum of three lists, the dilated structured vector, the gate vector, and the wiring vector. On the right is the inner product of the public input list with the powers of the constraint challenge. There are no separate rows left to pack, so Ragu needs no domain and no vanishing polynomial.

The remaining job is to let the verifier check this equation without seeing the structured vector. The last chapter already supplied the link to polynomials. A revdot product of two lists is the middle coefficient of the product of the polynomials with those lists as coefficients. So we read every list in the equation as coefficients.

The structured vector becomes the trace polynomial. In the last chapter's layout, the output wires take the lowest block of powers in order, the left inputs take the next block in reverse, and the right inputs take the block after that. The extra block is zero in our example.

Dilation multiplies each coefficient by the gate challenge raised to its position, which is the effect of substituting the gate challenge times X for X. So the dilated vector is the trace polynomial at a scaled input, and no new data is involved.

The gate vector and the wiring vector depend on the challenges, and the circuit is fixed before the challenges exist. So we describe them with polynomials in two variables, and substitute a challenge for the second variable once it is known.

In both, each coefficient goes at the partner of its wire's position in the trace, where two positions are partners when they mirror each other around the middle. A left input sits in the second block of powers, so its partner is in the third block, and the reverse holds for a right input. The wiring polynomial weights each linear constraint by a power of the second variable, standing for the constraint challenge. The gate polynomial holds, at the partner of each output wire, the negated weight of that output's gate.

The public input list likewise becomes the coefficients of the public input polynomial, whose value at the constraint challenge is the right side of the equation.

The Ragu Book's NARK chapter uses the other layout, with the left and right inputs swapped in the trace and the wiring polynomial. The wiring code at the commit this site pins places the left-input coefficients as we did. The two forms differ only by those names, and this site follows the code.

Now collect the dilated trace, the wiring polynomial, and the gate polynomial into one polynomial, which we'll call the second factor. The equation now says that the middle coefficient of the trace times the second factor equals the public input polynomial at the constraint challenge.

Our example uses the gate challenge five and the constraint challenge seven, from the last chapter. The trace has eight coefficients, nine, twenty-seven, nine, three, three, three, zero, zero, so the middle power is seven.

One entry from each part of the second factor shows where the numbers come from. In the dilated trace, the coefficient of X is twenty-seven times five, which is six modulo forty-three. In the gate polynomial, the top coefficient sits at the partner of the first output wire, and it is minus the sum of five cubed and five to the fourth, which is twenty-four.

In the wiring polynomial, the first left input sits at the power three of the trace, so its partner is the power four. Constraints zero, two, and three use that input with coefficients one, minus one, and one. Weighting each by seven to the constraint's number gives one, minus seven squared, plus seven cubed, which is thirty-seven modulo forty-three.

The coefficient of X to the seven in the product collects every pair of exponents that adds to seven, and those eight products sum to thirteen. On the other side, the public input polynomial is thirty times the variable cubed, and thirty times seven cubed is also thirteen modulo forty-three.

Why the coefficient is out of reach.

The full product has fifteen coefficients, and the one for X to the seven is thirteen, the value the equation requires. Every other entry is a by-product of the multiplication that the check does not constrain. The two highest are zero here, because the empty extra block leaves the trace with degree five.

In general, the trace and the second factor each have four times the gate count coefficients, so the product needs almost twice that many. Two obstacles keep the verifier from checking the middle coefficient directly.

The first is that an oracle answers evaluations, and one coefficient in the middle of a polynomial is not an evaluation at any point. The second is size. Ragu's oracles hold at most four times the gate count coefficients, because its commitment parameters contain that many points, so the product does not fit in one oracle. Doubling the points would fix this, but it would make every commitment in the system about twice as expensive, all to expose one coefficient.

Splitting the product.

A single reshaping removes both obstacles. For the size problem, cut the product into a lower half, running from the constant term up through the middle power, and an upper half with the rest. Each fits in one oracle. The coefficient we want is now the top coefficient of the lower half, which is still not an evaluation.

The one coefficient that evaluation can reach is the constant term, because substituting zero removes all the others. So we reverse the lower half's coefficient list, which moves its top coefficient to the bottom. Call the reversed lower half the first piece, and the upper half the second piece. The equation now says that the first piece at zero equals the public input polynomial at the constraint challenge.

Algebraically, the reversal substitutes the inverse of X into the lower half and multiplies by X to one less than the half's length. Each power then becomes its mirror image within the half.

In our product, the lower half is thirty-eight, thirty-nine, zero, nine, eighteen, twenty-nine, fourteen, thirteen. Reversed, the first piece starts with thirteen, so its value at zero is thirteen, the required value. The upper half, which starts nine, twenty-nine, thirty-nine, becomes the second piece.

The book calls these pieces c one and c two. They have nothing to do with the output wires of the last chapter, which now appear only inside the trace.

The verifier also needs a way to know that the pieces really came from the product. Reversing twice restores the original, so the same substitution applied to the first piece recovers the lower half. Adding the second piece, shifted up past the lower half, gives back the product. That one equation ties the pieces to the product, and the verifier has to evaluate it at a nonzero point, since it uses the inverse.

At the point nine, the inverse is twenty-four, because nine times twenty-four is one modulo forty-three. The first piece at twenty-four is six, and nine to the seventh is thirty-six. Thirty-six times six is one, which matches the lower half evaluated directly at nine.

Polynomial oracles.

We can now write Ragu's encoding as a protocol with oracles. Every oracle has degree bound one less than four times the gate count. The trace fits by construction, and the split exists so that the two pieces fit as well.

The order of messages carries much of the protocol's soundness. Both sides start with the wiring, gate, and public input polynomials. The prover sends the trace oracle, and only then does the verifier send the gate and constraint challenges, as the last chapter required.

The prover computes and splits the product, and sends oracles for the two pieces. Only then does the verifier send a random nonzero evaluation point. The pieces must be fixed before that point exists, because the split check is a random test of them.

The verifier asks the trace for its value at the evaluation point and at the point times the gate challenge. It asks the first piece for its values at the inverse of the point and at zero, and the second piece for its value at the point. It computes the public polynomials itself, and then it runs two checks.

The split check says that the trace value times the second factor's value equals the recombined pieces at the evaluation point. The target check says that the first piece at zero equals the public input polynomial at the constraint challenge. Dilation helps in the split check, because the verifier queries the same trace oracle at a second point. No separate polynomial is involved, so the prover cannot substitute a different trace in the second factor.

The verifier's local work varies. The gate polynomial has a short closed form, since its sums are geometric series, and the public input polynomial is cheap when the public input list is sparse. Computing the wiring polynomial directly costs time linear in the circuit size, and the chapter on wiring and the registry studies how to avoid this.

A complete run.

Take the witness with secret input three. The prover sends the trace oracle, and the verifier sends the challenges five and seven. The prover sends the two pieces, and the verifier sends the evaluation point nine. Nine times five is two modulo forty-three, and the inverse of nine is twenty-four.

The trace answers five at nine and nine at two. The first piece answers six at twenty-four and thirteen at zero, and the second piece answers thirty at nine. Locally, the verifier computes twenty-three for the wiring polynomial, three for the gate polynomial, and thirteen for the public input polynomial.

The split check multiplies five by the sum of nine, twenty-three, and three, which gives three, and the recombined pieces also give three. The target check compares thirteen with thirteen. Both pass, and the honest polynomials pass the split check at all forty-two nonzero points.

Why cheating fails.

The argument assumes that oracles are fixed when sent and respect their degree bounds, and that challenges are uniform and arrive after the messages they test. The next chapter's commitments provide the first assumption. They rely on the discrete log relation assumption, which says roughly that nobody can find a nontrivial linear relation among the public curve points. Fiat-Shamir provides the second in a non-interactive proof, treating its hash as a random oracle.

Inside this model, the argument only counts roots of polynomials. A prover with a false witness has to send some trace before seeing the two challenges, and the last chapter showed that a random pair rarely makes the true coefficient equal the target. For the secret input four, counting all one thousand eight hundred forty-nine pairs finds forty-three that do. Outside those, the honest split fails the target check, so the prover has to lie about the split.

The most direct lie changes only the coefficient the target check reads. At the challenges five and seven, the true coefficient is eighteen while the target is thirteen, so the prover changes the first piece's constant term to thirteen. The two sides of the split check then differ by five times X to the seven, and the verifier rejects at all forty-two nonzero points.

This lie is the easiest to catch, since the error sits on one power of X. But any pieces that pass the target check must describe a polynomial other than the true product. On the recombined side, the second piece only reaches powers above the middle, so the middle coefficient comes only from the first piece, as its value at zero. The target check forces that value to the target, while the true coefficient differs from it.

So the two sides of the split check always form a nonzero difference, and the prover's best option is to give it as many roots as possible. The degree bounds cap that number. The product has degree at most two less than eight times the gate count. The honest second piece leaves its top coefficient unused, but its oracle has room for one, and a cheater can fill it. So the difference has degree at most one less than eight times the gate count, and at most that many roots.

The prover can do better than the direct lie by spreading the difference over many powers. The product of X minus one, X minus two, and so on up to X minus fifteen has fifteen roots, and its coefficient of X to the seven is forty-one. Scaling it by nineteen, which is five divided by forty-one, keeps the roots and makes that coefficient five, the amount the true coefficient must change by.

The prover splits the true product minus this scaled polynomial, and the new first piece is thirteen at zero, as the target check requires. The split check now passes exactly where the scaled polynomial is zero. Testing every nonzero point finds fifteen passing values out of forty-two, the most a polynomial of degree fifteen allows. For two to the eleven gates on a field of about two to the two hundred fifty-five elements, the same limit gives a probability below two to the minus two hundred forty.

The two failure points add up to one bound. A cheater gets through either with a lucky pair of challenges, with probability at most one less than four times the gate count over the field size. Or, after an unlucky pair, it draws an evaluation point that is a root of the split check's difference, with probability at most one less than eight times the gate count over the field size. Together that is at most twelve times the gate count minus two, over the field size.

As with the QAP, the order of messages is essential. Suppose the prover also knows the point nine before sending the pieces. Changing the first piece's constant term moved the split check by five times nine to the seven. Adding a constant to the second piece moves it the other way by that constant times nine to the eight. The constant thirty-four, which is five divided by nine, cancels the two at this point, and the forged pair passes both checks at nine and nowhere else.

Comparing the two routes.

Both routes turn many constraints into one polynomial test at a random point. A QAP gives each row a domain point, encodes the witness as values at those points, and claims divisibility by the vanishing polynomial, with a quotient as the prover's extra polynomial. Ragu combines rows with powers of challenges, encodes the witness as coefficients of the trace, and claims one coefficient of a product, with the two pieces as its extra polynomials.

Groth sixteen uses one secret test point and secret setup values to tie its factors to one witness. Ragu's random values are all public, and one trace oracle, queried at two points, does the tying.

The central difference is division against extraction. A QAP has to show that a whole polynomial vanishes across a domain, and a quotient is the evidence for that. Ragu's claim concerns one number, so the prover computes no quotient and only moves that number to a place evaluation can reach.

The multiplication is not free, though. The prover still computes the product, and for large polynomials that takes fast Fourier transforms on a domain of about eight times the gate count. Ragu does not always pay this cost. Its uncompressed proofs send the two lists of the revdot product, and the verifier recomputes the product with one multiplication per entry.

Such a proof is larger and not succinct, but nobody runs a transform to build it, and the chapter on the complete proof explains when that trade is acceptable. The Ragu Book's structured vectors chapter places the split where the proof-carrying data tree needs succinctness, which is the compression step.

The encoding in Ragu.

The split appears in the compression step of the code at the commit this site pins, as a short function that cuts off the upper part and reverses what remains. The length it cuts at counts all the coefficients, so it plays the role of four times our gate count. The verifier recomputes the right side of the split check from the claimed evaluations and rejects on a mismatch.

Names differ across the book and the code. The book's NARK chapter calls the pieces c one and c two and the evaluation point x. Its structured vectors chapter and the code call the pieces p and q, and its compression chapter and the code call the point r. This site uses the NARK chapter's names, because r already names the trace and p is used for other polynomials.

The book and the code also differ on the public constant. The book's NARK chapter puts the constant one at the start of the witness and adds a check that the trace equals one at zero. The book's wiring chapter and the trace assembly code at the commit this site pins keep the first output wire at zero, so the trace is zero at zero, and put the constant one in an extra wire.

This site follows the code, and the chapter on the complete proof adds that wire to the toy circuit. Our toy circuit has no such wire. Its trace at zero is the wire value nine and its public input polynomial at zero is zero, so this chapter's run has no check on the trace's constant term.

The last point is reconstructed from the code at the commit this site pins, and the authors have not confirmed it. The uncompressed verifier recomputes the revdot product from the two lists. The split appears only in compression, where the prover applies it to a random combination of folded claims instead of a single product. The chapter on revdot folding returns to folded claims.

Where this leaves us.

A QAP interpolates each column of the R one C S matrices over a domain, so each row becomes an equation at its own point. The rows hold exactly when the difference is divisible by the vanishing polynomial, which reduces them to one identity with a quotient. A false witness has no quotient, so a prover passes only by luck or by knowing the test point. Groth sixteen enforces the test with a secret point, a trusted setup, and pairings, and Ragu uses none of those.

Ragu reads its consolidated equation as the middle coefficient of the trace times the second factor. Splitting the product and reversing the lower half turns that coefficient into a constant term, and a split check at a random point ties the pieces to the product. Written with oracles that have degree bounds, this is a polynomial I O P whose soundness depends on those bounds and on the order of its messages.

Every oracle in this protocol is still an assumption. The next chapter, Polynomial Commitments, builds the commitment that replaces each oracle with one curve point.
